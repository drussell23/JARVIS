Pause and predict

A signal has survived the event spine's debouncing and fingerprinting and a sensor has turned it into a SignalEnvelope. What questions do you think the final gate must still ask before the envelope may reach the pipeline?

Reveal the answer

The UnifiedIntakeRouter asks four: is it a duplicate of a recent signal (dedup_key), does it conflict with a file already under operation (file_lock), what is its priority score, and can it be coalesced with a recent similar envelope (coalesce_window). The output is a sorted priority queue with conflicts and coalescing already applied. See §56.

#### Check your understanding: PART IX — The Intake Layer

Conceptual questions

1. Why does the intake layer use four separate storm-protection layers instead of one strong deduplicator?

Each layer sits at a different stage and catches a different kind of repeat. FileWatchGuard absorbs bursts of file saves with a 0.3s debounce, checksums and an LRU cache; the TrinityEventBus drops identical events from many producers with a 60s SHA-256 fingerprint window; TestFailureSensor waits 2s before spawning pytest; and the router's envelope dedup_key stops duplicate operations. The paper calls the layers orthogonal: they compose, so an actionable event has already passed at least two of them. One deduplicator at the end would let every burst travel through the bus and spawn pytest runs before it was suppressed. See §55.2.

2. The intake layer is push-based, yet every sensor keeps scan_once() and its poll loop. Is that a contradiction?

No. Push is the primary path because it gives low latency: producers publish to the event spine immediately and sensors subscribe (Manifesto §3). The poll loops are kept as safety nets for when the event spine is unavailable, and scan_once() serves manual or CLI use. So push makes the common case fast, and polling makes sure detection still works when the push path fails. See §54 and §55.

3. The WAL exists for disaster recovery, but it also caused a bug. What was the bug, and what does the fix teach about recovery mechanisms?

The WAL in .jarvis/intake_wal.jsonl is replayed on restart so a crashed harness does not lose pending work. In Session N, replay put stale envelopes from a crashed session beside fresh ones, and coalescing merged them into one operation, half of it from the old session. The fix guards coalescing by session id, so envelopes from different sessions never merge, and stale entries are pruned by TTL. The lesson is that recovered state needs its origin recorded. Otherwise the recovery path quietly mixes old intent with new. See §56.2, §56.3 and §63.1.

Problem set

Problem 1 (trace). A developer saves a .py file twice within 0.2 seconds, and the change breaks a test. Trace the signal from the file save to a queued envelope. Name each component it passes and say which storm-protection layer acts at each step.

Hint

Follow the producer column of the event-spine diagram, then the four numbered storm layers, then the router's four questions.

Worked solution

The save is seen by FileWatchGuard (watchdog), via the Phase 1 FileSystemEventBridge. Its 0.3s debounce and checksum dedup fold the two saves into one change (layer 1). It publishes an fs.changed.* event to the TrinityEventBus, which drops any identical fingerprint seen within 60s (layer 2).

TestFailureSensor subscribes to debounced .py changes and waits 2s before spawning pytest (layer 3). The pytest plugin writes .jarvis/test_results.json, and the sensor emits a SignalEnvelope for the failure.

The UnifiedIntakeRouter checks the dedup_key (layer 4) and the file lock, scores priority, and checks whether to coalesce. It then places the envelope in the 16-slot priority queue, which is persisted to .jarvis/intake_wal.jsonl. See §54, §55.1, §55.2 and §56.

Problem 2 (design). A teammate says: "The paper tells us to rm .jarvis/intake_wal.jsonl before every session anyway, so let us delete the WAL entirely and keep the queue only in memory." Evaluate the proposal using the paper's reasons for the WAL and its account of the Session N bug.

Hint

Ask which problem the WAL solves and which problem the cleanup step solves. Are they the same problem?

Worked solution

The WAL is disaster recovery. When a harness crashes, replaying the log rehydrates the queue so pending work is not lost (§56.2). An in-memory queue would lose every pending envelope on a crash.

The cleanup step and the Session N bug are a different problem. Replay merged stale envelopes into fresh operations through coalescing (§56.3, §63.1). The structural fix is the session-id guard on coalescing, plus TTL pruning of stale entries. Neither requires removing the log.

So the proposal trades a real recovery guarantee for a problem that is already solved more narrowly. A better position is to keep the WAL and keep the session guard, and treat the manual cleanup as a clean-start step for controlled test sessions.

Problem 3 (code reading). Open backend/core/ouroboros/governance/intake/unified_intake_router.py and find _dedup_window_s and _is_duplicate. Which envelope source gets a different window? What are the two default window lengths in the router's config? What window value turns deduplication off? Relate this to storm-protection layer 4 in §55.2.

Hint

Search the file for voice_dedup_window_s. The config dataclass declares both defaults next to each other.

Worked solution

_dedup_window_s returns voice_dedup_window_s when envelope.source == "voice_human", and dedup_window_s otherwise. The config defaults are 300.0 seconds for voice and 600.0 seconds for everything else.

_is_duplicate returns False when the window is 0 or less, so a zero window disables deduplication. Otherwise it looks up the last monotonic time recorded for the envelope's dedup_key and reports a duplicate if that time falls inside the window.

This is layer 4 of §55.2, "envelope dedup_key prevents duplicate operations." The code adds one detail the paper does not state: the window is shorter for human voice commands than for sensor-generated signals.
