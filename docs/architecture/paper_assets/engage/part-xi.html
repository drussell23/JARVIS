Conceptual questions

1. Why did the arc run the ExplorationLedger in shadow mode (Session A) before enforcing it (Session B)?

Shadow mode shows what a new gate would decide without letting it block anything. In Session A, the ledger flagged a shallow pattern (score=3.00, one category, four read_file calls) that the legacy tool_calls >= 2 counter would have waved through. That was evidence that the new scorer sees something the old one misses, gathered before it had any authority. Session B then turned enforcement on and showed that the same pattern caused a hard rejection, which proved the toggle works. Session G showed the payoff: retry feedback made the model diversify its tools, so the ledger also steers behaviour as well as filtering it. See §62.1, §62.2 and §62.5.

2. Session S landed 0 of 4 files, yet the paper counts it as proof that multi-file enforcement works. Why is that a fair reading?

Session S was built to isolate one mechanism. The exploration gate was turned off so it could not hide the result. There were zero multi_file_coverage rejections in the log, and TestRunner saw all four target paths after the gate, so coverage enforcement did its job. The files did not land because of a separate problem: a type error sent the op to VALIDATE_RETRY and L2, which ran out of time before the idle timeout. The paper names that as Follow-up A, a VALIDATE/L2 timebox issue orthogonal to enforcement. Splitting "did the gate work" from "did the op persist" is what let the next sessions aim at the right bug. See §64.3.

3. What exactly was wrong with JARVIS_L2_TIMEBOX_S, and why was adding an INFO line that names both clocks part of the fix?

L2 was handed the op's drained ctx.pipeline_deadline, not its own timebox. In Session V, the setting was 600s, but L2 reported 120s remaining because that was all VALIDATE had left. The setting did not do what its name said. The fix computes L2's deadline fresh at dispatch (now + JARVIS_L2_TIMEBOX_S) and reconciles the pipeline deadline upward so later phases see a consistent clock. The mandatory INFO line records both clocks and which cap won, so the bug cannot hide again. In Session W it showed pipeline_remaining=0.0s beside winning_cap=l2_timebox_fresh. This fits the paper's pattern of hypothesize, instrument, confirm or falsify, fix, and verify in one session. See §65.3, §65.4 and §66.1.
