Quick check · §18

1. Which of Venom's four added capabilities targets patches written from "stale parameter-weight memory", and how?

Pre-patch exploration. Before writing code, the model reads the target files, searches related code and inspects the call graph, so the patch is based on the repository as it is now, not on what the model remembers from training (§18.1).

2. In the symbiote analogy, what does each partner lack without the other?

Without Ouroboros, Venom would be an unsupervised model making uncaged changes to disk. Without Venom, Ouroboros would be a rigid pipeline that cannot explore before acting. Together they give disciplined self-improvement (§18.2).

3. Why does the paper say O+V can enable tools by default when most frameworks require opt-in?

Because its containment is structural, not configurational: the Iron Gate (AST parser, command blocklist, path protection), the risk engine and the approval gates hold the line, not an environment flag (§18.3).

Quick check · §19

1. When the policy denies a tool call, does the loop stop?

No. The coordinator injects a tool_denied result into the conversation and carries on, so the model sees the denial on its next round and can choose a different action (§19.1).

2. How does a provider switch from a single API call to the agentic loop?

Both ClaudeProvider and PrimeProvider take an optional tool_loop. When one is supplied, generate() delegates to tool_loop.run(); when it is absent, the provider makes one call (§19.3). JARVIS_GOVERNED_TOOL_USE_ENABLED is the master switch (§19.2).

3. Why does every tool call become a ToolExecutionRecord?

So that the loop leaves an audit trail: each call is a ledger entry that can be inspected afterwards, alongside deadline and token-budget management that the coordinator also owns (§19.3).

Quick check · §20

1. What extra check does delete_file get beyond the path protections it shares with the other mutation tools?

A risk-tier check: deleting on multi-file targets or core paths escalates the operation to Orange (§20.5).

2. Why can ask_human not stall a generation forever?

It returns {"status": "timeout"} after 300 seconds if the operator does not answer, so the loop gets a result either way (§20.8).

3. Why do the three git tools need almost no Iron Gate check?

git_log, git_diff and git_blame are read-only. They report history and cannot change repository state, so there is no mutation risk to gate (§20.4).

Quick check · §21

1. Why are governance engine internals on the protected-path list?

So that the orchestrator cannot rewrite the orchestrator. The machinery that enforces the rules is itself out of reach of the tools it governs (§21.1, Rule 2).

2. Rule 9 is "default allow". Why is ending the ladder on allow not a loophole?

A call only reaches Rule 9 if every earlier deny rule has passed it. The deny rules encode the human's non-negotiable constraints; anything that survives them is, by design, the model's to explore (§21.1, §21.3).

3. What do Rules 7 and 8 protect against that Rules 1 to 6 cannot?

Volume rather than content. A call can be individually harmless and still be part of a runaway loop; the concurrency cap (default 2) and per-tool rate limits bound how many such calls run (§21.1).

Quick check · §22

1. How does the backend know which server should receive mcp_github_create_issue?

The name is server-qualified at discovery: mcp_{server}_{tool}. The backend resolves the server (github) from the name and sends it a tools/call JSON-RPC request for create_issue (§22.1, §22.3).

2. What does launching stdio servers with an argument array, never a shell string, prevent?

Shell injection. With create_subprocess_exec array form there is no shell to interpret metacharacters, so there is no injection surface at launch (§22.4).

3. What happens if a configured MCP server cannot be reached at boot?

The failure is logged but non-fatal; O+V boots without that server's tools (§22.5).

Quick check · §23

1. When does L2 take over, relative to VALIDATE's own retries?

Only after VALIDATE has exhausted its retry budget. L2 is the last convergence loop before POSTMORTEM, not a replacement for VALIDATE's retries (§23, §25).

2. Why classify each failure as syntax, test, environment or flaky?

The classification drives the decision step: retry budgets are class-specific, and the repair prompt carries the specific failure analysis into the next iteration (§23.2).

3. What does §23.6 say L2 changes about the pipeline's character?

Without L2 every validation failure ends the operation, so the pipeline is fragile to an imperfect first draft. With L2 it is convergent: it tolerates initial imperfection and works toward a fix (§23.6).

Quick check · §24

1. Why split the prompt at [TOOL RESULT] and [TOOL ERROR] markers?

Those markers delimit individual tool results, so each chunk is one whole result. Compaction then keeps or summarizes whole results and never cuts one in half (§24.2).

2. Why keep the most recent chunks rather than, say, the largest ones?

Recent chunks carry the context most relevant to the model's next turn. Older chunks have already been read and acted on, so only their profile (which tools, how many characters) is kept (§24.4).

Quick check · §25

1. Where do the Venom tool loop and the post-generation Iron Gate checks sit in the phase sequence?

The tool loop lives inside GENERATE. The Iron Gate checks (exploration-first, ASCII-strict) fire after GENERATE but before VALIDATE, so the candidate is judged structurally before any tests run on it (§25).

2. In the worked example, why does round 5 call run_tests after the patch is produced in round 4?

That is intra-generation verification: the model checks its own draft before submitting it, so a failing test can shape a revision before VALIDATE ever sees the candidate (§25, §18.1).
