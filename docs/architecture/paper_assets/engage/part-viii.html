#### Check your understanding: PART VIII — Edge Case Hardening (Twelve Refinements)

Conceptual questions

1. Refinement 11 (lock TTL) and Refinement 14 (file-hash stale guard) both deal with concurrent operations on one file. How do they differ in what they protect?

Refinement 11 protects progress. A crashed operation could leave a file locked forever, and every later signal for that file would queue behind it. Locks older than JARVIS_FILE_LOCK_TTL_S (300s) are therefore force-released with a warning (§52.4). Refinement 14 protects correctness. A candidate built from a read of file X at time T1 might be applied after another operation changed X. File SHA-256 hashes taken at GENERATE are compared again at APPLY to detect this (§52.7). The TTL can release a lock early by design, so the hash check is a second line of defence behind the DAG lock (§46). It catches stale candidates that the lock system did not prevent.

2. Refinement 15 merges same-file signals that arrive within 30 seconds, but lets HIGH-urgency signals skip the merge. What trade-off does that make?

Coalescing removes redundant work. Without it, several sensors that notice the same file within seconds would create N separate operations on the same target (§52.8). The price is latency: a signal may wait up to the window, 30s by default, in case others join it. For routine work that delay is cheap and the saving is real. For urgent signals the delay is the costly part, so HIGH urgency skips the buffer, because those signals "should not wait 30s for potential merges". The design accepts some duplicated work on urgent paths in exchange for responsiveness.

3. Several refinements make the system correct itself instead of relying on an operator. Pick two and explain what each one corrects, and against what evidence.

Refinement 18, the convergence metric, judges the lessons buffer by results. Every 10 operations after the first lesson, it compares the success rate before and after lessons. If lessons made things worse, it clears them (§52.11). Refinement 19, exploration budget control, judges model behaviour against a fixed budget. After JARVIS_MAX_EXPLORATION_ROUNDS (5) exploration-only rounds, it nudges the model to produce its change (§52.12). Both turn an open-ended failure, misleading guidance or an endless read loop, into a bounded one with a deterministic trigger. This is the §53 point: the fix is built into the architecture, not left to an operator noticing.

Problem set

Problem 1 (trace). At t = 0, operation A starts on parser.py and then crashes without releasing its lock. At t = 10s, two sensors each send a normal-urgency signal for parser.py. At t = 20s, a HIGH-urgency test failure for parser.py arrives. Using Refinements 11 and 15, describe what happens to each signal. When is the lock first eligible for force-release?

Hint

Coalescing (30s window) and the file lock (300s TTL) are separate mechanisms. Apply each one in turn.

Worked solution

The two normal-urgency signals arrive within JARVIS_COALESCE_WINDOW_S (30s) of each other for the same file, so they merge into one multi-goal operation (§52.8). The HIGH-urgency signal skips coalescing and goes straight to dispatch (§52.8).

Both the merged operation and the HIGH signal then hit the DAG check. parser.py is still registered to crashed operation A, so each is queued behind A (§46.1). A will never complete, so release_op will never run for it.

Refinement 11 breaks the deadlock. Locks carry timestamps, and _find_file_conflict() force-releases any lock older than JARVIS_FILE_LOCK_TTL_S, 300s by default, with a warning (§52.4). The lock first becomes eligible once it is more than 300s old, at about t = 300s, and it is released when the next conflict check runs. Until then even the urgent test failure waits, because skipping the coalescing window does not override a file lock.

Problem 2 (design). Refinement 14 (stale exploration guard) is currently a soft gate: a hash mismatch at APPLY gives a warning and a ledger entry. A reviewer wants it to be a hard gate that rejects the candidate. Using §52.7 and §53, argue both sides and say what evidence would justify the change.

Hint

The paper says why it is soft: "without blocking routine operations in low-concurrency scenarios". Ask what a mismatch means in each case.

Worked solution

For a hard gate: a mismatch means the candidate was built on stale file state. If applied, it "would overwrite the concurrent change", which is silent data loss (§52.7). A warning records the problem but does not stop it.

For keeping it soft: the paper says the soft gate exists to avoid "blocking routine operations in low-concurrency scenarios" (§52.7). When little runs concurrently, mismatches should be rare. A hard reject would throw away work that took a GENERATE call, and any false positive would cost real throughput. The DAG lock (§46) is already the first line of defence against two operations editing the same file.

The §53 approach points to deciding from evidence. The ledger entries the soft gate writes are that evidence. If they show mismatches that matched real lost edits, the structural fix is justified, and it could be narrow: hard-fail only when the hash differs and another operation is known to have written the file, or route the candidate back to GENERATE against the new state instead of rejecting it. If the ledger shows almost no mismatches, the soft gate is doing its job cheaply.

Problem 3 (code reading). Refinement 15 lives in backend/core/ouroboros/governance/intake/unified_intake_router.py. Find where _coalesce_window_s is read, the method _coalesce_key, and the dispatch-loop branch commented "HIGH urgency: bypass coalescing". What exact condition skips the buffer? How are envelopes grouped? What happens to envelopes that have no target files?

Hint

The docstring of _coalesce_key describes a soak that merged two unrelated problems into one operation.

Worked solution

The window is read as float(os.environ.get("JARVIS_COALESCE_WINDOW_S", "30")), which matches the 30s default in §52.8.

The bypass condition is envelope.urgency == "high" or self._coalesce_window_s <= 0. A HIGH signal, or a window set to zero or less, dispatches at once. Everything else is appended to _coalesce_buffer[key], and the time of first arrival is recorded. _flush_expired_coalesce_buffers dispatches each buffer once the window has passed since that first arrival.

_coalesce_key groups envelopes by their sorted target files joined with "|", which implements "same file" from §52.8. Envelopes with empty target_files do not share an empty key. They fall back to the envelope's provenance signature, and failing that to its unique idempotency_key, so they never merge. The docstring says why: soak bt-2026-05-17-213727 merged two distinct problems into one "Frankenstein" operation through the shared empty key. This edge case was found after the April paper and fixed in the same structural way §53 describes.
