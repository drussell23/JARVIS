Pause and predict

§5.3 said that Reactor, the Soul, runs O+V's tests and permitted bash commands in sandboxes with resource limits, process isolation and syscall filtering. Before reading on, predict where a generated candidate's tests actually run on origin/main today, and which isolation layer, if any, is switched off.

Reveal the answer

Not in Reactor. Reactor has no such code; its only sandbox is a Dockerized browser for its documentation scraper. Containment lives in the Body, inside O+V's VALIDATE phase. Tests run against a git-worktree copy of the candidate, candidate processes run in a PID namespace, test runs beside a soak go through a cgroup memory cap, and landings use per-operation worktrees. All of those are on. The Docker + seccomp runtime sandbox exists but is off. See §94.4.

Pause and predict

Reactor trains adapters and J-Prime serves them. Predict which component calls J-Prime to take the GPU and publish a newly trained adapter: Reactor, J-Prime itself, or something else? And what happens to O+V if Reactor is down?

Reveal the answer

Neither Reactor nor J-Prime. The Training Lifecycle Handoff, which is JARVIS code (observability/training_handoff.py), takes the lease, runs Reactor's trainer as a subprocess, converts the adapter and publishes it to J-Prime's registry. Reactor contains no call to the lease or adapter endpoints, and J-Prime calls no one. If Reactor is down, "the organism still works; it just stops learning": the recorder keeps writing to disk and the receiver catches up from its saved offsets. See §94.7.

#### Check your understanding: §94 — The Whole System: Four Subsystems, One Goal

Conceptual questions

1. The North Star says JARVIS should develop itself "fully autonomously", yet the same documents insist the operator remains the zero-order doll. Is that a contradiction, and where in the running code does the operator's role actually live today?

It is not a contradiction, because the documents define autonomy as a migration of authority, not its removal (§94.1). The operator moves from per-PR reviewer to batch approver to roadmap signer, and the PRD history lists what the North Star does not mean: the operator does not become irrelevant, safety gates are not removed, and even the top tier works inside an operator-signed roadmap, budget and scope. The Manifesto's line is that the organism "can write its own brain. It can never merge its own brain."

In code the boundary is concrete. The zero-push air-gap means O+V can land on local main but only the operator publishes (§93.7). The Order-2 review queue's amendment_requires_operator() is locked true, the recursion-depth gate blocks past a depth of 3 governance-touching APPLYs, and any change under governance/ forces approval (§94.10). The Conception Bridge stamps every self-filed proposal requires_human_ack=True (§94.9). So the end state is not a system without a human; it is one where the human's job has moved up a level, and §94.11 records that as the intended design, not a gap.

2. §94 repeatedly separates "built", "wired", "productive" and "default-on". Using one example of each gap, explain why the North Star's 2026-06-06 scorecard ("~30–35 %") and its 2026-09-19 revision ("~10-15%") can both be honest and still disagree.

Built but not wired: Bucket A, where 9 of 10 sampled modules still had zero live callers, and the M10 second-order driver with "0 references in orchestrator.py" (§94.8). Wired but off: the Epistemic Planner and Conception Bridge, both reachable but defaulting to false (§94.9). On but feeding the wrong consumer: north_star_context.py is on by default, but it feeds the DreamEngine's speculative prompt, not GENERATE. On and wired but defective: strategic_direction.py runs every time, yet tells the organism six principle titles and one paragraph instead of seven principles and the manifesto.

The June scorecard counted mechanisms that existed and marked tiers "CLOSED". The September revision re-verified by checking live callers, and found that the landings moved Order 1 "from nominally wired to actually productive" but "did not touch Order 2". Both assessments can be honest about what they measured; they measured different things. The paper treats the September figure as current because it measures reachability and effect, which is the lesson the reachability ledger (§93.12) was built to enforce.

3. Why does it matter that §5.3's "Reactor as sandbox" was wrong, beyond keeping the record straight? What would a reader who trusted §5 believe about containment that the code does not support?

§5.3 said permitted bash and run_tests execute inside Reactor, with resource limits, process isolation and syscall filtering, and that this "is what makes the Iron Gate's containment guarantees meaningful". A reader who trusted that would believe a second subsystem, on a separate boundary, contains anything the static checks let through.

The code says otherwise (§94.4, §93.16). Reactor is a training repository. Containment is in the Body: candidate trees, a PID namespace that "degrades to uncontained if the kernel refuses" unless the ..._REQUIRED flag is set, a cgroup memory cap, and per-operation worktrees. The layer that would do syscall filtering, Docker + seccomp, is off. That matters because the static cage has a measured at-scale escape rate of about 8.8%, concentrated in runtime-built eval/exec/subprocess strings that a static check cannot see (§93.3). The layers that bound damage when a candidate actually runs are real but narrower than §5 implied, and the strongest one described in April is not on.

Problem set

Problem 1 (trace). O+V generates a candidate test file for a signed goal; it passes, lands and survives. Follow that one candidate through all three loops of §94.7 until the model that wrote it has been retrained and the result could be published. At each boundary between subsystems, name the contract that carries it. Then say what happens if the handoff process dies after taking the lease.

Hint

Use the contracts table in §94.7. Loop 1 is seconds, Loop 2 hours, Loop 3 days; the human appears in only one of them.

Worked solution

Loop 1 (inference). The candidate generator routes to the local lane under the free-lane policy, and LocalPrimeClient calls J-Prime over the Ollama-native /api/chat or OpenAI /v1/chat/completions. Contract: the Ollama and OpenAI wire protocols. J-Prime answers with qwen3-coder-ov:30b, which is the base weights plus the active Reactor LoRA plus its sampling defaults (§94.5).

Loop 2 (learning). The trajectory recorder writes one ExperienceEvent line for the candidate into ~/.jarvis/trinity/events/. Contract: the shared JSONL schema, a file, not an HTTP call. Landing provenance adds git-proven landed and surviving labels to the hash-chained ledger, so this row becomes a success example (§94.6). Reactor's receiver tails the stream, and the GRPO reader reads the same files. The operator then runs the handoff on demand (autotrain is off): it refuses to run beside a live organism, acquires the lease (contract: token, TTL, freed MiB, state), runs run_grpo_training.py (contract: exit code 0/1/2/3 and a JSON report), converts the adapter to GGUF, publishes it with its sha256 (contract: a header-validated, versioned registry entry), releases the lease, and verifies greedily inside J-Prime's evaluation scope. The cycle ends COMMITTED or ROLLED_BACK.

Loop 3 (governance). The landed test sits on local main. Only the operator publishes to GitHub, and the standing rule is that no training-derived change is pushed without a held-out gain (§93.11).

Handoff dies holding the lease. The lease expires and J-Prime restores service through the same measured VRAM admission, so "expiry can never cause an OOM" (§94.5, §94.7). Until then, new generations get 503 with Retry-After, and an organism booting meanwhile exits with code 69.

Problem 2 (analysis). The A-level throughput criterion in PRD §6 is "sustained ≥ 1 commit per 30 minutes of session time", and PRD §34.9 scores it "Met in-window, not sustained". Using the cadence table in §93.10, compute landings per hour for the 09-26, 10-04, 10-05, 10-08 and 10-09 soaks, compare each with the threshold, and explain the verdict. Then say why §6's anti-goals would not count a faster model, by itself, as progress toward this criterion.

Hint

One commit per 30 minutes is 2 per hour. Count all landings, not only substantive ones, since the criterion says "commit".

Worked solution

Threshold: 2 landings per hour. 09-26: 3 / 1.97 h ≈ 1.52 per hour. 10-04: 3 / 2.98 h ≈ 1.01. 10-05: 10 / 6.03 h ≈ 1.66. 10-08: 0 / 1.25 h = 0. 10-09: 51 merged in about 9 h ≈ 5.7 per hour.

Only the 10-09 soak clears 2 per hour over its whole session; four of five fall below. That is what "met in-window, not sustained" means: the rate has been reached within a window but not held across sessions. The 10-05 soak also shows why "sustained" is hard: nothing landed from 22:24 to 00:29, which PRD §34 attributes to the supply wall (§93.10). Note too that the 10-09 row reports no substantive count, so its high rate is mostly tests for backend/api/*.

The anti-goals in §6 list "a smarter model", "more model calls" and "shipping faster" as things that do not by themselves count as progress (§94.8). A criterion is met by the observed outcome, sustained landed commits with a clean record, not by an input that might raise it. A faster or better model helps only if it moves the measured rate; and when yield is bounded by supply, it would not. The 2026-10-04 note adds the honest qualification that on the local 30B, model capability is a measured constraint, so it is not irrelevant, just not progress on its own.

Problem 3 (code reading). Open backend/core/ouroboros/governance/strategic_direction.py as it was at 21634caddb (before the fix described in §94.9) and read _MAX_DOC_CHARS, _extract_principles and _extract_manifesto. Find (a) the line that makes Principle 7 invisible once the README grows, (b) the end marker that truncates the manifesto, and why find matches it inside a "### " heading, and (c) a fix consistent with §94.9's description. What does the organism lose from its prompts because of these two defects?

Hint

Look at what slice of readme_content the principle regex iterates over, and at the third entry of end_markers. A string search for "## " does not care what character precedes it.

Worked solution

(a) _MAX_DOC_CHARS = 20_000, and _extract_principles runs its \*\*(\d+)\.\s+([^*]+)\*\* pattern over readme_content[:_MAX_DOC_CHARS]. Any principle heading that starts after character 20,000 is never seen. §94.9 measured Principle 7 at character 24,496, so the list stops at six. The docstring still says "Extract the 7 numbered principles".

(b) end_markers contains "## ", commented "next h2", and the code takes the earliest match after start + 100. But every level-3 heading, "### ...", contains the substring "## " starting at its second character, so find matches inside the first "### " sub-heading after the start. The section is cut at the first sub-heading, which §94.9 measured as 464 characters: only the opening paragraph.

(c) §94.9's fix: extract by heading rather than a fixed character window, and stop at a heading of the same level, for example by matching "\n## " at a line start and excluding deeper levels, and by locating each principle under the manifesto heading wherever it falls.

The loss: the organism is told six principle titles and one paragraph, and the principle it is not told is Absolute observability. The README, §3 and the module docstring all claim seven are injected; this is recorded as a measured correction in §93.16. It is a clean example of code that is on and wired but not doing what the documents say.
