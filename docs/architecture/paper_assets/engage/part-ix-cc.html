Quick check · §54

1. TestFailureSensor and TodoScannerSensor report latencies under 1s, while ScheduledTriggerSensor and WebIntelligenceSensor are "configurable". What explains the difference?

The fast sensors are triggered by pushed events, such as fs.changed.* on *.py or the pytest plugin, so they react as soon as the event arrives. The configurable ones depend on a cron schedule, web search results or idle detection, so their timing is set by configuration rather than by an event. See the table in §54.

2. OpportunityMinerSensor, TodoScannerSensor and DocStalenessSensor all react to fs.changed.*. Why are they separate sensors and not one?

They look for different things in the same event. One runs AST cyclomatic complexity analysis, one looks for FIXME/TODO/HACK markers, and one looks for undocumented modules. One file change can feed several independent detectors, each emitting its own SignalEnvelope. See §54.

Quick check · §55

1. In the push model, who pushes, and who subscribes?

Producers push: FileWatchGuard for file changes, the pytest plugin, the post-commit hook, and the bus bridges (GapSignalBus, EventEmitter, EventChannelServer). They publish to the unified TrinityEventBus at once. Sensors and other consumers, such as SafetyNet (L3) and FeedbackEngine, subscribe to it. See the diagram in §55.

2. Why does a pytest plugin write .jarvis/test_results.json, instead of the sensor running the tests itself each time?

The plugin captures results "during any pytest run" (Phase 2, §55.1). Every test run therefore becomes a signal, including runs that someone else started. The sensor does not have to own test execution to learn that a test failed.

3. A deployment registers three repos in repo_registry. How many TestFailureSensor instances run, and how is contract drift between the repos caught?

Three, one per repo, each watching its own test_results.json. Drift between repos is not caught by these per-repo sensors. It is caught separately by CrossRepoDriftSensor. See §55.3.

Quick check · §56

1. Two different signals, neither a duplicate of the other, target the same file. Which of the router's four questions handles this, and why is dedup not enough?

The file_lock check. Dedup only catches repeats of the same signal through its dedup_key. Two distinct signals can still conflict over a file that is already under operation, and the lock stops the second from dispatching against it. See §56.

2. Why does the router need a priority score at all, rather than serving envelopes first-in, first-out?

The queue is bounded at 16 slots. When it is full, something must be evicted, and the router evicts the lowest-priority envelopes. A score also decides dispatch order, since the router outputs a sorted priority queue. See §56 and §56.1.

3. The WAL is append-only. What two mechanisms keep it from filling up with old entries?

Entries are cleared when an envelope transitions to dispatched. Stale entries left by crashed sessions are pruned by TTL. See §56.2.
