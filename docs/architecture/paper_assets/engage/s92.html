Pause and predict

One battle-test session hung in GENERATE for over an hour because provider retry storms kept resetting the per-op idle counter. What kind of guard would stop this, and what signal must that guard refuse to listen to?

Reveal the answer

A hard wall-clock ceiling, --max-wall-seconds, which fires stop_reason=wall_clock_cap when the session runs too long. It is deliberately opaque to any activity signal, so a retry storm that looks like activity cannot keep resetting it. That is exactly how session #7 GENERATE S2 hung for 67+ minutes. Graduation soaks now set it, typically to 2400 s, about twice the 850–1300 s happy path. See §92.4.

Conceptual questions

1. Why do Treefinement L2 and the SWE-Bench-Pro harness ship with default-FALSE master flags and a clean-soak graduation criterion, instead of being switched on once their tests pass?

Passing tests shows that the code does what it was written to do. It does not show that the capability helps the live organism. The graduation contract in §92.15 says no capability graduates without empirical proof, and that proof comes from a clean-soak ladder, not from hand-tuning. Treefinement must show at least a 10% L2 success-rate lift, or at least a 20% wall-clock reduction at the same success rate, over at least two consecutive soaks (§92.13). Keeping the flag off also keeps rollback byte-identical: the legacy _run_inner is sha256-pinned, so turning the flag off restores exactly the old behaviour. The trade-off is speed. Capability sits dormant for weeks, as the 36-day minimum calendar in §92.9 shows.

2. The Adversarial Cage reported 0/38 escapes. What does this result support, and what does the paper itself say it cannot establish?

It supports the claim that the Iron Gate, Semantic Guardian and recursion bound stopped every one of 38 hand-authored attacks, with 12 detection gaps documented as predicted, not active (§92.4). It is a curated, hand-written set, so it is evidence about those inputs, not a measured escape rate across all possible attacks. §92.12 calls the cage "empirically zero-escape" and lists proving this as a formal property as an open question. §92.18 makes the limit explicit. Before Neurosurgeon, adversarial soaking can stand in for proof. Once the system modifies its own governance, only a formal proof can rule out a trajectory that escapes the bound.

3. IDE-native ReviewBranch builds preview branches with git plumbing and auto-rejects after 300 s. Why these two choices?

The plumbing commands hash-object, commit-tree and branch create a reviewable branch without touching the working tree, HEAD or the operator's index (§92.5). An autonomous proposal therefore never disturbs the human's own work in progress, yet VS Code's source-control panel still shows it natively. The 300 s default timeout ends in auto-REJECT, not auto-apply. If nobody looks, nothing lands. That replaces the old path, where a 5 s Rich overlay was followed by an automatic apply. The old behaviour is still available by setting JARVIS_REVIEW_TIMEOUT_S=0, so the safer default does not remove the operator's choice.

Problem 1 (trace). A Yellow-tier (NOTIFY_APPLY) operation produces a two-file diff at 14:00, and the operator is away from the keyboard until 14:10. Using §92.5, trace what happens to the diff, what the operator could see in their editor, and what state the repository is in at 14:10.

Hint

Look at which git objects ReviewBranch creates, what it never touches, and what its default timeout does.

Worked solution

ReviewBranch replaces the old 5 s overlay-then-apply path. It writes the candidate as git objects with hash-object and commit-tree, then creates a preview branch with branch. The working tree, HEAD and the operator's index are never touched.

The diff is recorded in the DiffArchive ring with a monotonic d-N reference, so it can be expanded later. VS Code's source-control panel shows the preview branch natively, and the SSE events reach the IDE.

The default JARVIS_REVIEW_TIMEOUT_S is 300 s. With no decision by about 14:05 the review auto-REJECTs. At 14:10 the working tree is unchanged, the candidate was never applied, and its audit record remains in the archive. Only with the timeout set to 0 would the legacy auto-apply have landed it (§92.5).

Problem 2 (design). A contributor proposes that --max-wall-seconds extend itself automatically whenever an operation is making progress, for example when the provider is still returning events, so that slow but healthy sessions are not cut off. Using §92.4, critique the proposal and suggest what to do about slow sessions instead.

Hint

Ask which failure the wall-clock cap was built for, and what that failure looked like from the inside.

Worked solution

The cap exists because an activity-based guard was already defeated once. Provider retry storms reset the per-op liveness counter, and session #7 GENERATE S2 hung for 67+ minutes while looking busy (§92.4).

A cap that extends on "progress" brings back the same weakness. A retry storm emits events, so it looks like progress and the cap never fires. The paper says the cap is "opaque to any activity signal" precisely so that it cannot be defeated this way.

The answer for slow but healthy sessions is a larger fixed margin. Graduation soaks use about 2400 s, roughly twice the 850–1300 s happy path. The ceiling stays a pure function of elapsed time, so no state inside the system it guards can hold it open.

Problem 3 (code reading). §92.1 describes the mutation cage as a "structural COUNT gate (second-rejection after the type gate)". Open backend/core/ouroboros/governance/scoped_tool_backend.py and find the count gate. Answer three questions: in what order the two gates run, at what moment a mutation slot is consumed, and what happens to the slot if the inner backend then fails.

Hint

Search for mutation_budget_exhausted and read the lines just after the refusal block.

Worked solution

Layer 1 is the type gate. A tool outside the dispatched allowed_tools set is refused as POLICY_DENIED before anything else runs. Layer 2, marked "count gate (mutation budget)", runs only for mutation tools. If _mutations_count has reached _max_mutations, it logs reason=mutation_budget_exhausted and returns POLICY_DENIED, noting that the budget is set at dispatch and cannot be extended mid-op.

Otherwise the slot is consumed before the call is delegated: self._mutations_count += 1. The comment explains that a failure inside the inner backend still burns the slot on purpose. This stops a model from retrying a failing mutation until it exceeds the budget.

The call is also recorded and _sync_state_mirror() is updated before delegation. That is the state_mirror behaviour §92.1 credits with keeping the audit trail intact across a hard kill.
