Pause and predict

In most autonomous-AI systems, more safety means less autonomy. After reading twelve hard gates, predict: does adding more Iron Gate rules give O+V less autonomy or more? Why?

Reveal the answer

More. Because the gate is structural, operations that pass it do not need human approval. Default-allow tools are safe, and low-risk operations auto-apply because the gate has already vetted them. The trade-off flips: more Iron Gate means fewer approvals and so more autonomy. Approval remains only where the gate cannot decide (APPROVAL_REQUIRED). See §60.

#### Check your understanding: PART X — The Iron Gate: Safety Philosophy

Conceptual questions

1. Why must the Iron Gate be pre-linguistic and model-uninfluenced, rather than a careful reviewer that reads the model's reasoning?

The paper's claim is that an autonomous system is safe only if its safety layer cannot be talked out of its decisions. A gate that reads natural language can be persuaded by a well-argued rationale. The Iron Gate reads only file paths, AST nodes, tokens, exit codes and command strings, so no prompt can change its verdict. The protected-paths example makes this concrete: a model that "reasons" about why it needs to modify .env is still refused. Determinism and logging then make every decision repeatable and auditable. See §57 and §58.2.

2. The paper accepts that the gate will sometimes reject a valid operation. Why is that an acceptable cost?

§59 says the gate is not an oracle. False positives are acceptable because a rejected operation can be retried with different inputs. The errors the gates exist to stop are often irreversible: rm -rf /, a forced push to main, leaked credentials, unbounded spend. A conservative, hand-curated rule that sometimes says no costs one retry. A clever rule that sometimes says yes to the wrong thing can cost the repository. Keeping one deterministic rule per gate, with no voting and no intent reasoning, keeps each verdict predictable. See §58.3 and §59.

3. Gates 8, 9 and 12 (approval timeouts, worker ceilings, file-lock TTL) do not inspect code at all. Why do they belong in a safety inventory?

They protect liveness rather than correctness. An unanswered approval would block forever without the 600s timeout that moves it to CANCELLED. A wedged worker would hold a pool slot forever without the wall-clock ceiling. A crashed operation's file lock would starve every later operation on that file without the 300s TTL. Each is still a deterministic rule the model cannot override, which is the paper's definition of an Iron Gate. A safe system has to keep making progress, not only avoid bad writes. See §58.8, §58.9 and §58.12.

Problem set

Problem 1 (trace). An operation's ROUTE phase expects four files. The model makes one read_file call. It then returns a candidate whose files: [...] list covers three of the four files, and one file contains a stray non-ASCII codepoint. Which post-GENERATE gates react, and what does each do? Can this candidate reach VALIDATE?

Hint

Three gates live at the orchestrator's post-GENERATE checkpoint. Check each one against the candidate separately.

Worked solution

Gate 4 (exploration-first): one call is below the default minimum of 2, so the candidate cannot proceed to VALIDATE (§58.4).

Gate 5 (ASCII strictness): the codepoint is caught and, if possible, auto-repaired with an ASCII approximation. Only a failed repair would cause rejection (§58.5). On its own, this gate would not stop the candidate.

Gate 6 (multi-file coverage): three of four declared files are covered, so the gate rejects. A partial multi-file change would leave the codebase inconsistent (§58.6).

The candidate does not reach VALIDATE. The paper does not give an order for these checks, but either Gate 4 or Gate 6 alone is enough to stop it. None of these verdicts depend on the model's explanation of why it acted as it did.

Problem 2 (design). Someone proposes replacing the hand-curated bash blocklist (Gate 3) with an LLM judge. The judge would read each command and decide whether it is dangerous, so it can catch new destructive patterns the list misses. Critique the proposal using Part X's philosophy and trade-off.

Hint

Check the proposal against the five properties in §57 and the four "is not" statements in §59.

Worked solution

An LLM judge breaks the properties that define the gate (§57). It reasons about language, so it is not pre-linguistic. Crafted input can influence it, so it is not model-uninfluenced. The same command could get different verdicts, so it is not deterministic. §59 also says the gate is explicitly not an AI.

It would weaken §60's argument too. The autonomy dividend exists because a structural gate needs no human backstop. A persuadable judge would push the operator back toward approvals, so autonomy would shrink.

A defensible variant keeps the blocklist as the authoritative gate, since the paper calls it expandable, and uses any model only as an advisory signal. For example, the model could propose new patterns for a human to add to the list. It would never decide whether a command runs.

Problem 3 (code reading). Open backend/core/ouroboros/governance/multi_file_coverage_gate.py. Read the module docstring and check_candidate. What does the function return when the gate passes, and what when it fails? What happens for an operation with zero or one target file? What gate number does the file use for itself, compared with §58.6?

Hint

The return contract is spelled out at the end of the docstring. The single-file case is one of the first checks in the function body.

Worked solution

check_candidate returns None when the candidate is fine. Otherwise it returns a tuple (reason, missing_paths), and the missing paths are echoed back to the model in retry feedback.

If the operation has one target file or none (len(targets) <= 1), the gate no-ops. It also no-ops when JARVIS_MULTI_FILE_ENFORCEMENT is set to false. Otherwise every target path must appear in the candidate's files list, and a legacy single-file candidate on a multi-target op is rejected with every target listed as missing. That matches §58.6.

The docstring calls the file "Iron Gate 5" and explains the Session O background. §58.6 numbers it Gate 6 in the inventory, while §64.3 and §64.4 in the session log also say "Iron Gate 5". The numbering is not consistent across the paper. The gate's behaviour is the same either way.

The file also contains later slices the paper does not cover, such as a subset-coverage exception for resolved test-to-source attribution.
