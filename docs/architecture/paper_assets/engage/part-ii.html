Pause and predict

A fix must edit one file in the Body repo and one in the Mind repo. The Body edit applies cleanly, then the Mind edit fails. What should the system do, and what end states should it never allow?

Reveal the answer

It should undo the Body edit. The Saga pattern walks already-applied patches in reverse order and reverts each through ChangeEngine.rollback(), a step called compensation. The only allowed end states are fully applied or fully reverted; a half-applied contract change would break the protocol between the two repos. See §7.1 and §7.2.

#### Check your understanding: PART II — The Trinity Architecture

Conceptual questions

1. Why does Venom's bash and run_tests execution happen inside Reactor Core rather than on the Body's own shell?

The Body has privileged access to the operator's screen, keyboard, audio and filesystem. Reactor Core provides sandboxes with resource limits, process isolation and syscall filtering. Running model-requested commands there means that even a command the Iron Gate permits cannot reach the Body's privileges directly. The paper says this separation "is what makes the Iron Gate's containment guarantees meaningful": the gate decides what may run, and the sandbox limits what a permitted command can touch. See §5.1 and §5.3.

2. The Governed Loop Service only delegates submit() to the orchestrator and does no pipeline work itself. What does this separation buy?

The Service is a lifecycle manager: it wires providers, runs health probes, keeps the file-touch cache and the Oracle index loop, and handles clean startup and shutdown. The pipeline's phases live in the orchestrator. Because of the split, adding or changing a phase does not require touching the Service. It also keeps responsibilities clear: the Service ensures every in-flight operation is completed or gracefully abandoned, while the orchestrator owns phase transitions. See §6 and §6.2.

3. Why is the CrossRepoVerifier needed if every repo patch has already passed validation on its own?

Each patch validated in isolation only proves that repo is internally consistent. A multi-repo change exists because two repos must agree, for example on an HTTP contract between Body and Mind. Only tests that run across the union of patches can check that agreement. So the verifier runs after all patches apply and before commit, and if it fails the Saga compensates even though every individual patch was valid. See §7.1 and §7.2.

Problem set

Problem 1 (trace). A Saga carries a 2c.1 candidate with patches for jarvis, jarvis-prime and jarvis-reactor, applied in that dependency order. All three apply, but the CrossRepoVerifier fails. Trace what happens next, in order, and state the final state of each repo.

Hint

Compensation walks the applied patches in a specific direction, using the undo descriptor each RepoPatch recorded.

Worked solution

Each RepoPatch recorded an undo descriptor when it was applied (§7.2). The verifier runs after all patches apply but before commit, so nothing has been committed yet.

Its failure triggers compensation even though each patch validated alone. The Saga walks applied patches in reverse: first jarvis-reactor, then jarvis-prime, then jarvis, each reverted with ChangeEngine.rollback().

All three repos end in their pre-operation state: "fully reverted", never partially applied. The rest of the pipeline treats this as one operation, since only APPLY knew it was a Saga (§7.3). See §7.2.

Problem 2 (design). A contributor suggests that every pipeline phase should loop over repos, so CLASSIFY, GENERATE and VALIDATE each run once per repo in a Saga. Using §7.3 and §6.2, argue for or against this, naming what the current design protects.

Hint

Ask who would need to understand Saga semantics under each design.

Worked solution

The current design runs the phases once per operation and lets only APPLY dispatch to SagaApplyStrategy (§7.3). That keeps all 11 phases uniform and lets a reader follow the orchestrator without knowing Saga semantics.

Looping every phase over repos would spread multi-repo logic into every phase, so every phase author would need to handle partial progress across repos. It would also split one operation into several partial ones, which works against the single all-or-nothing result the Saga guarantees.

The same principle appears in §6.2: the Service delegates to the orchestrator so that pipeline changes do not ripple into lifecycle code. Encapsulating complexity in one place is the pattern. The argument favours keeping the current design. See §6.2 and §7.3.

Problem 3 (code reading). Open backend/core/ouroboros/governance/governed_loop_service.py. (a) Find the ServiceState enum and compare its members with the diagram in §6.1. (b) Search for _file_touch_cache and find the cooldown guard. What are its window and hit-count constants, and which phase does a blocked operation advance to?

Hint

The guard sits under a comment beginning "Cooldown guard"; look at the return inside the loop.

Worked solution

(a) ServiceState has six members: INACTIVE, STARTING, ACTIVE, DEGRADED, STOPPING and FAILED. These match the six states in the §6.1 diagram.

(b) The guard sets _COOLDOWN_WINDOW_S = 600.0 (ten minutes) and _COOLDOWN_MAX_HITS = 3. For each target file it keeps a deque of timestamps keyed by the resolved path, drops entries older than the window, appends the current time, and blocks if the count exceeds 3. So the fourth touch inside ten minutes is the one blocked, which matches §6's "three touches" description.

A blocked operation calls ctx.advance(OperationPhase.CANCELLED), so in code the "hard block" takes the form of a cancellation, and a warning is logged naming the file and op id. See §6.
