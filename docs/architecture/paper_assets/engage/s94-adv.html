Advanced conceptual questions

A1. §92.17 treats the core C as provider-agnostic and puts all the growth in the shell Sn. §94.10 maps C onto the model J-Prime serves and says Reactor is how "the core itself changes". What does a changing core do to the bounded-RSI conjecture's three claims, and why does that make the held-out-gain rule a doll requirement rather than just a quality bar?

In §92.17 the iteration is (C, Sn) → δ → δ′ → Sn+1. Only the shell changes; C is a fixed thermal source. Claim (a), monotone deterministic entropy of the shell, and the "only tighten" invariant of §94.10 are statements about Sn. Claim (c) is the one that refers to the core: net agentic entropy is bounded by a constant "depending on C's base capacity and Sn's growth rate".

Once Reactor closes Loop 2, C is no longer fixed. Each committed adapter is a new C (§94.10). The constant in (c) is then a moving target, and (b), the shell's restraint on C's unconstrained output, was only ever argued for a given C. A new core could in principle produce candidates that sit in exactly the regions the shell does not bound. The empirical evidence for that region exists: the static cage misses about 8.8% of mutated escapes at scale (§93.3).

That is why §94.10 calls the held-out-gain rule "the doll's own requirement applied to the core": the core may grow only if something outside it measures that it got better. The rule is enforced outside C (a benchmark from human commits with hidden tests) and outside the shell (the operator alone publishes, Loop 3). I would add a limit the paper does not claim to cover: the held-out rule measures capability, not containment. It checks that C improved, not that Sn still bounds the improved C. Evidence that would settle whether this matters is re-running the at-scale mutation harness (§93.3) against candidates drawn from each new adapter and checking that the escape rate does not rise.

One more synthesis point. §92.17 lists "a new test" among the ways M extends the shell. 84 of the 91 landings are new test files (§93.10). In the conjecture's own vocabulary, most of what the Mechanic has done so far is grow Sn, while the one completed training cycle has not yet shown that C grew at all (§93.11).

A2. The training handoff and the organism must never hold the GPU at the same time. List every mechanism in §94.5–§94.7 that enforces this exclusion, say which side each protects, and identify a crash window the paper does not fully specify.

Five mechanisms, from both ends. (1) The handoff "refuses to run beside a live organism" (§94.7), which protects training from an organism generating mid-cycle. (2) The organism checks the lease at boot and exits with code 69 if the lane is lent (§94.5, §93.9.2), which protects the cycle from an organism started during it. (3) DRAINING refuses new generations with 503 and Retry-After and waits for in-flight ones, and an in-flight response holds a reference so its model cannot be evicted mid-answer, which protects any generation already running. (4) RELEASED is declared only when nvidia-smi shows the memory free, which protects the trainer from starting into memory that is still held. (5) Lease expiry restores service only through measured admission, which protects serving from an OOM when the handoff disappears.

The exclusion is therefore enforced by measurement at the GPU, not only by agreement between processes: "'We sent terminate' is not evidence; the card is." Child processes bound by a kill-on-close Job Object or PR_SET_PDEATHSIG close a further hole, a crashed engine leaving an orphan holding VRAM.

The window the paper leaves open is a crash after publication and before verification ends. §94.7 says the cycle ends COMMITTED or ROLLED_BACK, and a losing candidate is rejected through the registry with the incumbent restored and re-verified, but it does not say what the registry holds if the handoff dies between those steps. What the paper does guarantee bounds the damage: versions are never overwritten, activation rewrites the model declaration atomically (so the served model is one version or the other, never half of each), the origin adapter remains as the fallback of last resort, and nothing training-derived is published to GitHub without a held-out gain. The evidence that would settle the open question is a fault-injection run that kills the handoff at each step and reads GET /v1/adapters/{model} and the served identity afterwards.

A3. PRD §6 lists "a smarter model" as an anti-goal, yet one of the four subsystems, Reactor, exists to make the model smarter. Is the Trinity's learning loop working against its own definition of done? Argue a position and name the evidence that would settle it.

My position: no, provided Reactor's output is judged by the §6 criteria and never by its own training metrics. The anti-goals list inputs that do not count as progress: a smarter model, more sensors, more knobs, bigger context, more model calls, shipping faster (§94.8). The point is that A-level is defined by observed outcomes such as sustained throughput, reliability and cross-session learning. An adapter is an input like the others. The 2026-10-04 note qualifies the first anti-goal: on the local 30B, model capability is a measured constraint (§33), so improving it can be a means. It cannot be the measure.

The design already reflects that distinction in three places. The handoff's own gate (4/6 against 3/6) was rejected by the project's notes as evidence of learning (§93.11). The operator's push rule requires a held-out gain, not a training-loss improvement. And the reward is a tiered verifier anchored in what the pipeline needs (envelope, shape, syntax, substance), not in model-centric scores (§94.6).

There is a real way the loop could work against the goal, though. Cross-session learning, one of the seven dimensions, is defined in PRD §6 as postmortem-driven prompt changes visible in later operations, and it is "Not measured". If effort flows into adapters because Loop 2 is the visible, finished pipeline, the unmeasured dimensions stay unmeasured. The evidence that would settle the question is a two-step test: first a held-out gain for an adapter (§93.15 step 2), then a change in an A-level measurement, for example landings per hour on a fixed goal mix, attributable to that adapter. A held-out gain with no change in landed work would show the loop improving the model without moving JARVIS toward done.

Challenge problems

Challenge 1 (adversarial). Assume a future in which the Epistemic Planner and Conception Bridge are armed and the Sentinel runs at its default ceiling. Construct three routes by which the organism might loosen its own governance without the operator choosing to: (1) the planner files a step "advance 'Reliability' in governance/<some gate>.py" that, once generated, lowers a threshold; (2) an adaptive Anti-Venom component mines postmortems and proposes relaxing a guardian pattern that blocked several good candidates; (3) a Reactor adapter, trained on landed work, becomes systematically better at producing candidates the static checks accept. For each, find the layer in §94.9, §94.10 or §93.7 that stops it, or show honestly that none does and what would.

Hint

Separate three things: who decides the work enters (intake), who approves the change (Sentinel, boundary gate, Order-2 path), and what a change to the core rather than the shell is subject to.

Worked solution

Route 1: self-filed governance edit. The bridge stamps every envelope source="auto_proposed", low urgency and requires_human_ack=True, so the proposal cannot proceed until a human acknowledges it (§94.9). Even after an acknowledgement, the boundary gate forces approval for any change under governance/; the Sentinel always escalates Order-2 self-modification and anything touching the cage (§93.7); and the recursion-depth gate blocks past three consecutive governance-touching APPLYs (§94.10). There is one honest caveat. The Sentinel's auto-approval ceiling defaults to APPROVAL_REQUIRED, and the paper does not say how the boundary gate's forced approval interacts with that ceiling for a governance file that is neither in the Order-2 manifest nor part of the cage. §93.10 shows governance-package files (dw_capacity_probe.py, candidate_generator.py) did land under signed, operator-sanctioned goals. So the decisive stop for this route is the human acknowledgement on the proposal, not the approval gate alone.

Route 2: adaptive loosening. Stopped by construction. The adaptation ledger "refuses to persist loosening proposals"; adaptive gates may only tighten; any loosening must go through the Order-2 amendment path, whose amendment_requires_operator() is locked true; and no adaptation is autonomous, since every proposal goes to the operator's queue (§94.10). This is the shell's monotonicity invariant, claim (a) of §92.17, enforced in code.

Route 3: a core that games the shell. No shell layer stops this, because nothing in the shell changes: the adapter changes C. What bounds it is outside both. The adapter must win a held-out evaluation and the operator alone publishes (§93.11, Loop 3); the registry can reject or roll back an adapter, and a rejected version can never be reactivated (§94.5). But the held-out benchmark measures solved tasks, not escape behaviour, and the static cage already misses about 8.8% of mutated escapes (§93.3), while Docker + seccomp, the runtime layer that would catch runtime-built eval/exec, is off (§94.4). Honest conclusion: the design does not currently test whether a new core is harder to contain. A proposal (mine, not the paper's): add the at-scale mutation escape rate, run on candidates from the new adapter, to the handoff's verification step, and reject any adapter that raises it.

Check: routes 1 and 2 each meet at least two independent human-authority points; route 3 meets only the publication key, which is why it is the weakest.

Challenge 2 (quantitative). §94.9 and §93.15 say that arming the planner before the supply wall is fixed "produces a longer queue, not more landings". Model it. Givens from the paper: the planner writes at most 3 steps per synthesis; every bridged envelope carries requires_human_ack=True; the pre-wall rate was about 1.52 substantive landings per hour (09-26 soak, §93.10); the 10-09 soak produced 219 whole-file answers against 6 diffs (§93.8, §93.14). Assumptions (not in the paper): the planner synthesizes once per hour and 2 of its 3 steps pass the bridge's EV floor; the operator acknowledges 10 proposals per day; each acknowledged proposal edits an existing file. (a) Compute the arrival rate of proposals and the growth of the acknowledgement backlog. (b) Bound the landing rate the proposals can add after the wall. (c) Use Little's law to find the wait in the ack queue after one week. (d) State what this says about the order of §93.15.

Hint

The human acknowledgement is a server in series with the pipeline. A queue whose arrival rate exceeds its service rate has no steady state; its length grows linearly. The diff fraction is an upper bound on how often an edit to an existing file is even in the right format.

Worked solution

(a) Arrivals: 2 per hour × 24 = 48 proposals per day. Service at the ack step: 10 per day. Utilisation ρ = 48/10 = 4.8, far above 1, so the queue is unstable. The backlog grows by 48 − 10 = 38 proposals per day.

(b) Throughput through the ack step is capped at 10 per day, about 0.42 per hour. Each acknowledged proposal edits an existing file, which goes down the 2b.1-diff path. In the 10-09 soak only 6 of 225 answers (6 diffs against 219 whole-file) were diffs, about 2.7%. Being a diff is necessary, not sufficient, for landing, so 2.7% is a generous upper bound on landing per proposal. Added landings ≤ 0.42 × 0.027 ≈ 0.011 per hour, roughly one every four days, against the 1.52 per hour the loop achieved on evidence-sourced work before the wall.

(c) After 7 days the backlog is about 38 × 7 = 266 proposals. Little's law, W = L/λ, applied to the service rate at which the queue drains (10 per day, since that is the rate items leave), gives the wait a newly arrived proposal faces: 266/10 ≈ 27 days. Strictly, Little's law describes a steady state, which this queue does not have; the figure is the wait at that moment, and it grows by 3.8 days for every day the planner stays armed.

(d) Both bottlenecks the model exposes are named in §93.15. The ack queue shows that arming the planner turns the operator into the server, which is exactly the outcome the North Star exists to avoid: otherwise the operator "becomes the bottleneck on every Trinity expansion arc" (§94.1). The format bound shows that the proposals would die at the leading failure mode. Step 1 (diffs land) raises the 2.7%, step 3 (wider supply) keeps evidence-sourced work flowing past the wall, and only then does step 4 add arrivals the system can serve. Check: if the operator could acknowledge 48 per day and the diff rate were near 100%, the same model gives a stable queue, so the conclusion depends on the two measured bottlenecks, not on the assumed planner cadence.

Challenge 3 (cross-Part trace). The operator, at the assistant, says "JARVIS, write tests for the audio error fallback." Trace that utterance as far as the code on origin/main can take it on the current host, using §94.3 for the Body, the intake and approval path of §93.7, and the pipeline of §94.4. Identify exactly where it stops today, what works instead, and which item in PRD §34.9's sequence closing the gap corresponds to.

Hint

Look at what the voice surfaces bind to, and what the host is. Then ask which typed seam reaches the same intake.

Worked solution

In code, the path exists. backend/voice/jarvis_voice_bridge.py routes code tasks to a VoiceCommandSensor, which the intake layer constructs and the supervisor binds to the voice bridge; the intake router maps the voice_human source to it (§94.3). From intake, the envelope would go through the orchestrator's phases (CLASSIFY → ROUTE → … → GENERATE, which calls J-Prime → VALIDATE in a candidate tree under a PID namespace → GATE → APPLY → VERIFY), land in a sovereignty worktree, pass the promotion gate and fast-forward onto local main (§94.4, §93.7).

Where it stops. At the first step. The voice surfaces depend on macOS frameworks (CoreAudio, AppKit and others), and on WSL2 they have nothing to bind to, so the assistant half of the Body is effectively dormant on this host (§94.3; the paper notes this is inferred from imports, not a live probe). Second, O+V no longer boots through the supervisor here; ov boots its own six-layer stack, so the supervisor binding that connects the voice bridge to the sensor is not the path in use. Third, even on a Mac, the README says the voice loop "has never completed a full cycle in production". The link that would join a Mac Body to the Windows engine (ov link, JARVIS_LINK_BRIDGE_ENABLED) is off by default.

What works instead. The operator types the request in the cockpit: either as conversation, which becomes an intake envelope with source operator_chat, or as /goal sanction / /goal inject (§94.3). From there the trace above applies unchanged, and a test-file request is the 30B's strongest kind of work (84 of 91 landings, §93.10). The landing would stay on local main; publishing remains the operator's act.

Which step closes it. Step 4 of PRD §34.9, the JARVIS → O+V handoff through the /goal seam, marked not started (§94.9). Note the ordering: the seam it names is the typed one that already works, so the gap is the assistant surface reaching that seam, not the pipeline. Check: the claim "in code, yes; in practice, not yet" in §94.3 is exactly this trace.
