#### Check your understanding: PART XIV — The Road Ahead

Conceptual questions

1. Why does "Functions, Not Agents" reframe DoubleWord instead of dropping it?

The 2026-04-14 tests showed DW's streaming endpoint could not sustain agent-shaped workloads (§77). But the non-streaming /v1/chat/completions endpoint with stream=false had never been exercised by O+V (§77.1). So the evidence condemned one transport and one workload shape, not the provider. Treating DW as an untested function provider lets it carry short, structured, non-streaming calls, which could take a large share of structured inference load without going near the streaming stall (§77.5).

2. In the Phase 3 BlastRadius design, the 397B score can only raise the risk tier, never lower it. Why?

The deterministic import-graph score stays as the floor, and the model score can only escalate (§77.4). This preserves the invariant that fluid intelligence never lowers a hard gate. If a model could de-escalate risk, a wrong or hallucinated answer could weaken a safety decision. Letting it only escalate means a model error can at worst make the system more cautious. The anti-hallucination check on invariants_touched adds a second guard: names not found in the diff cause rejection and a deterministic fallback.

3. Why does §78 demand three consecutive successes under comparable conditions, instead of counting Session W as proof?

One success may be luck. The Manifesto's §6 treats a single success as a data point, and graduation to "capability" needs three in a row (§78). "Comparable conditions" (same pipeline, Iron Gate settings and provider topology) stops a later success from being produced under easier settings. The no-regression requirement makes sure the gain did not come at the cost of the seven capabilities or the Iron Gate. The paper calls the bar deliberately conservative, to avoid false confidence.

Problem set

Problem 1 (trace). With Phase 3 live, an op changes one line: a retry-backoff constant. The import graph shows almost nothing depends on that file, so the deterministic BlastRadius score is low. The 397B analyst returns a higher score and lists an invariant name that does not appear in the diff. Trace what happens to the risk score.

Hint

Check the anti-hallucination gate before you apply the escalate-only rule.

Worked solution

The 397B output follows the blast_radius.1 schema, including invariants_touched (§77.4).

The anti-hallucination gate requires invariants_touched to be a subset of symbol names extracted from the actual diff. One listed name is not in the diff, so the output is a hallucination and is rejected.

On rejection the system falls back to the deterministic score. So the final score is the low structural one, and the risk tier is not escalated by this call.

This shows the cost of the guard: the case in §77.4 (a one-line backoff change with large real impact) is exactly what the model is meant to catch, but a malformed answer loses that benefit. Had the invariant names been valid, the higher score could have raised the tier, never lowered it.

Problem 2 (design). Someone proposes fixing §79.1 by making the 'infra' failure class retryable, so a flake on iter=1 no longer kills the op. Compare this with the paper's proper fix, and explain what the proposal would hide.

Hint

Ask why the same unchanged candidate gets two different classifications.

Worked solution

The symptom is that the same unchanged candidate is classified 'test' on iter=0 and 'infra' on iter=1 (§79.1). The classification is non-deterministic, and that is the actual defect.

Making 'infra' retryable treats the symptom. It would also change behaviour for real infrastructure failures, which are non-retryable by design, so genuine sandbox problems could now loop through retries.

The paper's proper fix is sandbox isolation between iter=0 and iter=1, so the same candidate yields the same classification. That removes the flake at its source and keeps the meaning of 'infra' intact.

It also matches the framing of §79: these load-bearing workarounds must be addressed before multi-file autonomy can be considered production-hardened, and a retry rule change would just be another workaround.

Problem 3 (code reading). Open backend/core/ouroboros/governance/context_compaction.py. §77.3 says the deterministic summarizer is "type-counting plus phase-histogram" and that a semantic strategy is consulted with a deterministic fallback. Find the deterministic summarizer and the method that consults the strategy, and say what the strategy method returns when no strategy is injected, and when the strategy raises an exception.

Hint

Look at _build_summary and the method defined right after it.

Worked solution

_build_summary (around line 536) is the deterministic path. It counts entries by type (falling back to phase or role), counts phases seen, and finds the time span, then formats a string like "Compacted N entries: ... Phases covered: ...". Its docstring says "No model inference."

The next method, _build_semantic_or_fallback, consults self._semantic_strategy, which is set from the semantic_strategy constructor argument. If the strategy is None or not enabled, it returns the deterministic summary unchanged.

If strategy.summarize raises, the exception is logged and the deterministic summary is returned. The docstring also says that in shadow mode the deterministic summary is always returned while the strategy still runs for telemetry.

One detail differs from the paper's wording: the delegation lives in this separate method rather than inside _build_summary itself. The behaviour matches §77.3: any failure falls back to the deterministic path.
