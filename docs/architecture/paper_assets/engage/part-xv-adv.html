Advanced conceptual questions

A1. §91 claims "true CC-parity" for seeing a screenshot of a bug. The proof in §87 ran on Claude. Under the October configuration in §93.6, which parts of that claim still hold, and what live test would re-establish it?

The intake half still holds, because it does not depend on the provider. Both ingress paths still converge on ctx.attachments (§83), and the hoist, the Attachment schema and the five gates do not change with the lane. The provider half is different. With JARVIS_PAID_LANES_ENABLED=false, Claude is never constructed (§93.6), so the document and image blocks of §85.1 are never sent.

The only active lane is J-Prime. For jprime the serializer emits OpenAI-style image_url blocks and drops PDFs with a WARNING (§85.2, §89.5). So a PDF attached today is dropped, and the op runs text-only. The §85.2 escape hatch, JARVIS_PROVIDER_OVERRIDE=claude-api, names a provider the paid-lane authority keeps switched off.

Images are the open case. They would be sent, but the model serving code generation is qwen3-coder-ov:30b, and §93.6 says the vision model (jarvis-vision:8b) is declared in J-Prime but at the time of writing is still partly served by Ollama. The paper gives no live-fire proof that the local lane reasons over image bytes at GENERATE.

So in October the parity claim holds for the architecture and is unproven for behaviour. The test that would settle it is the §87 method on the local lane: an image with a unique, unguessable string, run through scripts/attach_livefire.py, passing only if the reply quotes the string verbatim. It would also need both breadcrumbs from §85.4 under one op_id. Note that the §85.4 line is labelled [ClaudeProvider], so the breadcrumb to grep for may differ on J-Prime.

A2. The intake hoist fails closed by demoting a broken attachment op to text-only, logged at DEBUG (§83.3). §93.12 later added capability assurance, which refuses to run below the declared envelope instead of degrading silently. Should an /attach op whose file vanished still run? Argue it per kind.

The two principles conflict here. §83.3 chose availability: a stale frame, a deleted file or a failed mime check must not break intake, so the op still enters CLASSIFY without pixels. §93.12's capability assurance chose honesty: an operation should not run with less than it declared it needs.

My position (a proposal, not described in the paper) is to decide by kind. For sensor_frame, demotion is right. The useful signal has already been pulled out at the sensor: OCR text, the Tier-1 verdict and the matches travel in evidence["vision_signal"] (§83.1). A text-only op can still act on "a traceback is on screen", and Ferrari may have died between scan and intake (§89.1).

For user_provided, demotion is misleading. The operator asked something like "what is misaligned here?" about a specific file (§90.2). Without the image the model answers a different question, and the operator has no visible sign of it because the only trace is a DEBUG line. That is the silent degradation §93.12 exists to refuse. The better behaviour is to fail the op visibly back to the REPL.

The evidence to settle it is already in the logs. Using the §90.3 grep rollup, count envelopes that carried user_attachments but have no matching attachments_hoisted line, and check whether their answers referred to the missing content. If that count is near zero, the question is academic. If not, the per-kind split matters.

A3. The multi-modal arc needed five contract fixes before one signal could be emitted (§82.2), even though every component existed. Connect this to §87's live-fire method and §93.12's DARK-feature finding. What general rule about proof does the paper end up adopting?

Every component in §82.1 worked on its own terms. The frame server wrote frames, the sensor scanned, the serializer could encode blocks. Each producer and consumer pair disagreed on one detail: the filename, the timestamp key, the hash format, a missing ocr_fn, and a purpose allow-list without "generate". Each mismatch failed silently, for example ferrari_absent every 60 s while Ferrari was healthy, or no_regex_match ocr_chars=0. Unit tests on either side would pass, because each side matched its own idea of the contract.

§87 answers this with an end-to-end behavioural test. Real bytes go to the real API, and the test passes only if the reply contains a string that could not have been guessed. No single-side test can pass that check by agreeing with itself.

§93.12 shows the same pattern at system scale: 131 features with the flag on, the module present, and no production caller. The reachability ledger's three stages (registered, invoked, effective) apply §82.2's lesson to every feature. The arc's own unblocking step was the same idea in small form: commit 44305f7e96 instrumented the silent-skip paths before deeper debugging (§88).

The general rule is that a capability counts as present only when a live run shows it being invoked and having its effect. Having the code, the flag and the unit tests is not enough. §93.10's "first-order proof" applies the same standard to commits: an autonomous landing counts only when it did real work for a signed goal and git confirms it.

Challenge problems

Challenge 1 (adversarial). §83.2 says /attach reuses Venom's _is_protected_path() as step 5 of its validation perimeter. Write an envelope that gets a file inside a protected location sent to a provider at GENERATE without going through that check. You may use any producer the paper shows calling router.ingest. Identify every gate it passes, and say whether anything in the paper's design stops it. (Reference: the hoist is in backend/core/ouroboros/governance/intake/unified_intake_router.py, and Attachment.from_file is in backend/core/ouroboros/governance/op_context.py.)

Hint

Compare where the protected-path check runs (§83.2) with where the hoist builds Attachments (§83.3). §87.2 shows a producer that builds the envelope itself.

Worked solution

Where the check lives. In §83.2, the protected-path check is step 5 inside SerpentFlow._handle_attach(), at the REPL edge. The hoist in §83.3 reads evidence["user_attachments"] and calls Attachment.from_file(path, kind="user_provided") directly. In the repo, the hoist in unified_intake_router.py calls from_file with no protected-path call, and from_file in op_context.py checks only for a non-empty absolute path, that the file exists, and that the extension is whitelisted. A search finds no _is_protected_path call in the intake router.

The envelope. §87.2 shows scripts/attach_livefire.py building an IntentEnvelope with make_envelope() and calling router.ingest() itself, with no REPL. Any in-process producer can do the same, including a future ingress like the Slack webhook §83.4 anticipates. Give it source="voice_human", urgency="critical", empty target_files (allowed because user_attachments is present, §86 commit 12c), and one entry whose path is an absolute path under a protected directory with a .png or .pdf extension and a size of 10 MiB or less.

Gates it passes. At the hoist: absolute path, file exists, whitelisted extension, mime inferred from the extension, and hash8 computed from the bytes. In __post_init__: kind, mime, hash format and path length are all valid (§84.1). In the serializer (§84.4): the purpose is generate, the kill switch is on by default, the context is non-empty, and the route is IMMEDIATE, not BG or SPEC (critical plus voice_human, §87.5). The per-attachment read is within 10 MiB. Then the bytes are base64-encoded and sent.

What stops it. Nothing in the paper's design, for any file that has a whitelisted extension. The extension whitelist does narrow the target: a file such as .env has no whitelisted extension, so from_file raises and the hoist demotes the op to text-only. Note also that the mime type comes from the extension, not from the file's content, so any bytes renamed to .png pass the schema.

A proposed fix (not in the paper): run _is_protected_path() inside the hoist or inside from_file for user_provided, so every ingress inherits the check. This matches §83.4's own rule that new ingresses only add a kind at the hoist. Today a new ingress would have to remember to call the check itself. Check your answer by asking which layer is reached by every producer: only the hoist is.

Challenge 2 (quantitative). §84.1 allows up to 8 attachments per context (_ATTACHMENT_MAX_PER_CTX), and each may be up to 10 MiB. §84.2 says 10 MiB inflates to about 14 MiB of base64, "well below" the 32 MiB Anthropic limit. Compute the worst-case payload for a full context, find the largest number of maximum-size attachments that still fits under 32 MiB, and say which of the five gates in §84.4 would stop an oversize request. What happens if a ninth attachment is supplied?

Hint

Base64 turns every 3 bytes into 4. Check whether any gate in §84.4 looks at the total across attachments.

Worked solution

Per attachment. 10 MiB x 4/3 = about 13.3 MiB of base64. The paper rounds this to about 14 MiB.

Full context. 8 x 13.3 = about 107 MiB (8 x 14 = 112 MiB with the paper's rounding), before any prompt scaffold. That is more than three times the 32 MiB figure.

Largest set that fits. Two maximum-size attachments are about 26.7 MiB, leaving about 5.3 MiB for the system text and tool manifests. Three are about 40 MiB, which is over the limit. So the safety margin in §84.2 holds for one attachment, and roughly for two. From three upwards it does not.

Which gate stops it. None of the five. Known-purpose, env-kill, non-empty context and live-route are all yes/no checks. The read budget is per attachment: each file is read with the 10 MiB cap, and in the repo _serialize_attachments in providers.py calls att.read_bytes() for each attachment without any running total. The 8-per-context cap counts attachments, not bytes. So a three-attachment op reaches the provider and risks exactly the payload-oversize 400 that §84.2 says the budget is meant to avoid.

A ninth attachment. In op_context.py, with_attachments raises if there are more than _ATTACHMENT_MAX_PER_CTX entries. The hoist wraps everything in one try/except (§83.3), so the whole hoist fails and the op runs with zero attachments, not eight. A request over the count limit loses everything, while a request over the byte limit is sent anyway.

A proposed fix (not in the paper): add an aggregate byte budget in the serializer, derived from the provider's payload limit minus a scaffold reserve. Over budget, drop the later attachments with a WARNING, which matches §88's rule that a violating attachment is "dropped at the nearest boundary with a WARNING log". Check: 2 x 10 MiB x 4/3 = 26.7 MiB is less than 32, and 3 x 10 x 4/3 = 40 is more.
