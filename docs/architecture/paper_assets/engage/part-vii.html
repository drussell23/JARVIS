Pause and predict

You want the model to read the target file before it writes a patch. Is a strong instruction in the prompt enough? If not, where would you enforce the rule, and how would you stop the model from faking exploration?

Reveal the answer

A prompt is not enough, because a model can ignore instructions. O+V does both. The prompt states the protocol, and the Iron Gate checks the tool records after GENERATE and before VALIDATE. A violation goes back through GENERATE_RETRY with targeted feedback. The newer ExplorationLedger gives repeated calls no credit. Failed calls add to the score but not to category coverage, so flooding the gate with junk calls cannot pass it. See §47.1, §47.2, §47.3 and §47.4.

#### Check your understanding: PART VII — Autonomous Developer Intelligence (Seven Capabilities)

Conceptual questions

1. In the ExplorationLedger, failed tool calls add to the score but not to category coverage. Why split them this way?

A failed call is still information. A grep that finds nothing tells the model something, so it is fair for the call to add to the score (§47.4). Coverage is the property the gate is really after: did the model look at the code from different angles? Examples are comprehension, call graph and history (§47.3). If failed calls counted toward coverage, a model could fire off cheap failing calls, reach the floors and pass without having read anything. Duplicate calls get zero credit for the same reason: progress means new files and new queries, not repeated fetches (§47.3). The gate needs all three conditions together: the score, the number of categories and the required categories.

2. VALIDATE has already passed. Why does O+V run tests again in VERIFY, and what did the Refinement 10 bug show about this?

VALIDATE tests a sandbox copy of the candidate. VERIFY tests the files actually written to disk. The two can disagree. Some tests read from the filesystem, import order can differ, and state such as database connections is real only in VERIFY (§48.3). VERIFY runs only the tests that cover the changed files, so the check stays affordable, and failures go to L2 repair (§48.1). The Refinement 10 bug shows why "on disk" matters. L2 produced a fix that was never written to disk. It was re-checked against the sandbox, which passed, and the operation "completed" without the fix landing. Writing the fix with change_engine.execute() before VERIFY re-runs closed that gap (§48.2).

3. Session lessons have two separate safeguards: the infra-poisoning guard and the convergence metric. What failure does each one prevent, and why are both needed?

The infra guard works before injection. It tags failures such as DoubleWord timeouts as "infra" and keeps them out of the prompt. Otherwise the model might learn a false lesson such as "avoid calling DW", when the right response was simply to retry (§49.3). The convergence metric works after injection. Every 10 operations after the first lesson, it compares the success rate before and after lessons existed. If the rate has gone down, it clears the buffer (§49.4). The guard filters out one known kind of bad lesson. The metric catches any lessons that turn out to hurt, including code lessons that looked valid. Together they mean the lessons buffer is only kept while it helps.

Problem set

Problem 1 (trace). Start from the three pending signals in the §50.2 table (A at -2, C at 4, B at 6). Add signal D: source test_failure (base 2), urgency high, 3 files, confidence 0.92, no dependency credit. Compute D's priority and the new dispatch order. Then suppose D and A both target foo.py. What actually happens to D at dispatch time?

Hint

High urgency is worth 1, and 2 to 4 files cost 1. Then apply §46 to the shared file.

Worked solution

D = 2 - 1 (high urgency) + 1 (3 files is within 2 to 4) - 1 (0.92 is at least 0.9) - 0 = 1 (§50.1). The order is A (-2), D (1), C (4), B (6).

Priority decides only who is dispatched next. It does not override file locks. A dispatches first and registers foo.py in _active_file_ops. When D comes up, _find_file_conflict returns A's op id, so D is parked in _queued_behind[A] (§46.1). C can be dispatched in the meantime if its files do not overlap.

When A completes, release_op frees foo.py and re-ingests D automatically. The retry path computes D's priority again (§50.3). D is then planned against a file that now includes A's patch (§46.2). If A crashed instead, the 300s TTL would force-release the lock so D is not stuck forever (§46.3).

Problem 2 (design). An operator finds the 5-second NOTIFY_APPLY window annoying and suggests moving every yellow-tier change to SAFE_AUTO (silent). Another operator suggests moving every yellow-tier change to APPROVAL_REQUIRED. Using §45 and §51, explain what each change would cost.

Hint

The paper calls the yellow tier a "trust-building mechanism". Ask what each extreme does to that trust.

Worked solution

The yellow tier covers new files, multi-file changes and core orchestration paths (§45). These are riskier than a single non-core file, but not risky enough to need a sign-off. The 5-second window tells the human before the change lands and lets them cancel, without requiring them to act (§45.1).

Making the tier silent removes the moment where a problem can be caught. The paper's improvement loop depends on that moment: when a bad yellow change slips through, the operator steps in and the rules are refined. Silent changes would also undercut intent visibility (§44), because multi-file changes would land without the operator watching.

Making the tier blocking would turn every multi-file change into a wait on a human, which is the outcome the yellow tier was invented to avoid. It would also clog the priority queue: §51 pairs severity with cost-aware priority so valuable work moves under suitable oversight, not under a blanket wait. A better answer keeps the window and tunes its length (Refinement 17 makes the delay configurable through JARVIS_NOTIFY_APPLY_DELAY_S, §52.10), or adjusts which rules put a change in yellow.

Problem 3 (code reading). §46 cites unified_intake_router.py. Today the file is backend/core/ouroboros/governance/intake/unified_intake_router.py. Find _find_file_conflict and the place where _file_lock_ttl_s is read from the environment. What is the default TTL? What does the current code check before it deletes a stale lock, and why would a plain "if older than TTL, delete" be unsafe?

Hint

Look for a comment that mentions "CAS" and for _active_file_ops_lock.

Worked solution

The TTL is read as float(os.environ.get("JARVIS_FILE_LOCK_TTL_S", "300")), so the default is 300 seconds. This matches §46.3 and Refinement 11 (§52.4).

Inside _find_file_conflict, the code takes _active_file_ops_lock for each target file. It reads the (op_id, registered_at) entry and computes its age. If the age is over the TTL, it reads the entry again and deletes it only if both the op id and the timestamp are unchanged. This is a compare-and-swap (CAS). On deletion it logs the "Force-releasing stale file lock" warning that §46.3 describes. If the entry changed in the meantime, the code aborts the delete and logs at debug level.

A plain age check followed by a delete has a race. Between reading the stale entry and deleting it, another register_active_op could write a fresh lock for the same file. A blind delete would remove that live lock, and two operations could then edit the file at once, which is the self-conflict the DAG exists to prevent (§46). The paper describes the TTL. The code adds a later hardening so that the TTL fix cannot itself remove a lock that is still in use.
