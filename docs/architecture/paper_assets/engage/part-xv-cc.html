Quick check · §82

1. Why did the sensor report degraded reason=ferrari_absent even while Ferrari was writing fresh frames?

The server wrote metadata to frame_meta.json, but the sensor checked for latest_frame.json. Its liveness test, os.path.exists on its own metadata path, therefore failed on every scan. Contract violation 1, §82.2.

2. The server's dhash was a correct value. Why did the evidence still get dropped?

The server wrote the raw Python integer, which stringifies to decimal. The schema validator requires 16 lowercase hex characters, so the evidence envelope was dropped at validation. The fix formats it with f"{dhash_val & 0xFFFFFFFFFFFFFFFF:016x}". Contract violation 3.

3. Why did the missing OCR function fail silently rather than with an error?

scan_once only calls OCR when self._ocr_fn is not None. The construction site never passed one, so the OCR text stayed empty and every scan ended as skipped: no_regex_match ocr_chars=0, which looks like a normal outcome. Contract violation 4.

Quick check · §83

1. Why do VisionSensor envelopes have an empty target_files?

When the sensor emits, the op only means "there is a detected condition on screen". It has no file target yet. The orchestrator infers targets downstream from the OCR content, the app context and goal-relevance scoring. Empty is the honest value. See §83.1.

2. What does step 5 of the /attach validation reuse, and what happens if that helper cannot be imported?

It reuses Venom's _is_protected_path(), the same helper that guards edit_file, write_file and delete_file against .git/, .env, credentials and FORBIDDEN_PATH memories. If it becomes unimportable, the check fails closed instead of being skipped. See §83.2.

3. What does the finding_cooldown stage key on, and what does it prevent?

It keys on the tuple (verdict, app, matches) for 120 seconds. The same on-screen finding seen again in the next frames does not emit a new envelope each time. See the diagram in §83.1.

Quick check · §85

1. How does the Claude serializer choose between an image block and a document block?

It branches on att.mime_type. application/pdf becomes a document block, and any other allowed mime becomes an image block with that media type. See §85.1.

2. Where do the media blocks go relative to the prompt text, and why?

Before it: user_content = [*_image_blocks, {"type": "text", "text": p}]. Claude's prompt guidance recommends media first for the best reasoning quality.

3. In the multi_modal log line, why can blocks be smaller than attachments, and is bytes the payload size?

blocks counts the blocks actually emitted, which can be fewer if some attachments were dropped at the per-attachment read gate. bytes is the sum of on-disk sizes, not the base64-inflated payload. See §85.4.

Quick check · §89

1. frame_server.py processes die after 6 to 7 minutes when the Terminal loses focus. Why is that acceptable for the sensor?

The supervisor reliably respawns them. In the 1 to 30 second gap, the staleness guard correctly emits degraded reason=frame_stale, and the scan loop resumes on the first fresh frame. See §89.1.

2. Attempt 3 of the VisionSensor graduation failed. Why does the paper say this was not a sensor flaw?

macOS rate-limits background processes bringing windows to the foreground, as an anti-hijack policy. The probe's Terminal window could not stay frontmost, so the traceback never reached the display's pixels. The sensor graduated on 2/2 clean captures plus the structural proof. See §89.3.

3. What future change would let DoubleWord and J-Prime reason over PDFs, and why was it left out?

A PDF-to-image adapter, for example pdf_to_png via PyMuPDF, emitting one image per page up to a page cap. It was scoped out so the provider-side contract would not grow while the Claude path was being stabilized. See §89.5.
