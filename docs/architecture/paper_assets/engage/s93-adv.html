Advanced conceptual questions

A1. §93.10 counts 91 autonomous landings by the Co-Authored-By: Ouroboros+Venom trailer on main. Name three ways that number differs from "useful changes the organism made that are still in the codebase", and which §93 mechanism measures each difference.

First, a commit stays in history after it is reverted. The count includes f97f8195d6, where only a punctuation rewrite landed and which was reverted by c8430f9b6a. §93.14 also lists a hollow landing that was reverted. A trailer count measures commits made, not changes that survive. Landing provenance (§93.11) measures that difference: it attaches git-proven landed and surviving labels, and 35 of 39 landings were proven.

Second, "landed" is not "useful". 84 of the 91 add test files. The documentation landing that flattened the author's name, and the sse_contract.py landing whose dropped content was restored by hand, still count as one each. §93.10 handles this by splitting landings into kinds and by the separate "substantive" column in the soak table. The trailer alone cannot carry that judgement.

Third, the trailer is text, and text by itself proves nothing. The counting rule works because it combines the trailer with presence on main, which only promotion can produce. The promotion gate does not trust the co-author line either. Its provenance check in accumulation_promotion_gate.py requires the Op-ID, Session and Files trailers, and requires that the session named in the trailer also appears in the branch name. GoalReconciliationLedger then binds goal to commit through git ancestry (§93.7).

So the trailer count is a good upper bound that anyone can recompute with git log. That is its real advantage over session summaries, which undercounted (§93.10). Turning it into a measure of value needs the provenance labels and the substantive classification on top of it.

A2. §92.18 defines the Neurosurgeon threshold as autonomous mutation of "iron_gate.py, semantic_guardian.py, or other governance code under an autonomous signature". Three of the five production landings in §93.10 modified files in the governance package. Why does §93.10 still say Mechanic? Is that a principled refinement or moving the goalposts?

§93.10 adds two qualifiers that the §92.18 sentence did not spell out. The change must touch the governance substrate (a safety gate or the cage), and it must be on the organism's own initiative. The three landings, dw_capacity_probe.py and two edits to candidate_generator.py, were made under signed, operator-sanctioned goals and did not touch a safety gate.

I would argue the refinement is principled, because it follows the reason §92.18 gives for the threshold. Neurosurgeon matters because past it "only a formal proof of containment … can rule out" an escaping trajectory. A capacity probe that backs off a failing provider does not change what the shell lets through. An edit to the cage does.

There is a subtlety the reader should catch. "Signed" cannot be the test for operator initiative, because Goal Discovery signs its own goals with the same key the operator uses (§93.7). The real distinction is the goal's source: the roadmap or /goal sanction on one side, discovery or the proposal inbox on the other.

The design also turns the threshold into an approval decision. BLOCKED operations, Order-2 self-modification and anything touching the cage always escalate, whatever the Sentinel's tier ceiling (§93.7). The evidence that would mark a real crossing is a landing on a cage file under a self-sourced goal. By that design, such a landing cannot happen without an operator approving it. The goalposts would only be moving if §93 had redefined "the cage" to exclude a file it had already changed, and it has not.

A3. Suppose the Epistemic Planner were armed today, before step 1 of §93.15 (making diffs land) is done. Trace the second-order effects through Goal Discovery's ranking, the diff path and the training corpus.

The planner's work enters through the proposal inbox, ranked below evidence, and is signed by the same single signer (§93.7). At first, then, it would mostly wait behind red tests and uncovered modules. Its effect would grow as the supply wall hits. After about four hours on uncovered modules, evidence-sourced work runs out (§93.10), and planner proposals would become most of what dispatches.

Those proposals are model-invented work, so most of them would edit existing files rather than create test files. That puts them straight onto the weakest path: existing files must answer in the 2b.1-diff schema, and the 10-09 soak produced 219 whole-file answers against 6 diffs (§93.8, §93.14). So the queue would fill with work that mostly dies at the leading failure mode. §93.15 says this outright: arm the planner only after (1)–(3), "so the backlog does not fill faster than it drains".

The corpus effect is quieter. Every candidate becomes a recorder row (§93.11). A flood of failed whole-file rewrites would push the corpus further toward the shape that already ruined the first training run, where 86% of prompts asked for whole-file rewrites that could not fit the completion window. Output-contract tags (§93.11) let Reactor train only on current formats, which limits the damage, but the useful contrast per GPU cycle would still fall.

Net effect: more operations, a lower landing rate per GPU hour, and a noisier corpus, with no gain in landed commits until diffs land. That is why §93.15 orders the steps the way it does.

Challenge problems

Challenge 1 (quantitative). Use the cadence table in §93.10. (a) Pool the four completed soaks that report a substantive count (09-26, 10-04, 10-05, 10-08) and compute landings per hour and substantive landings per hour. (b) The 10-05 session ID encodes its start as 01:27:17, it ran 6.03 h, and nothing landed from 22:24 to 00:29. Work out where that gap sits in the session. (c) Project substantive landings for a 9-hour soak under a constant-rate model and under a supply-wall model. (d) Treating landings as a Poisson process (an assumption), how surprising is the gap at a constant rate? (e) Square your answer with the ~9 h 10-09 soak and its 51 merged commits.

Hint

Add 6.03 h to the start time and compare the result with the clock time at which the gap ends. The two clocks differ by a whole number of hours.

Worked solution

(a) Wall time: 1.97 + 2.98 + 6.03 + 1.25 = 12.23 h. Landings: 3 + 3 + 10 + 0 = 16, which is 1.31 per hour. Substantive: 3 + 2 + 6 + 0 = 11, which is 0.90 per hour.

(b) 01:27:17 + 6.03 h (6 h 01 m 48 s) = 07:29:05. The gap ends at 00:29, so the table's clock runs exactly 7 hours behind the ID's clock (consistent with UTC against Pacific daylight time, an inference). 22:24 on the table's clock is 05:24 on the ID's clock, 3.95 h into the session. The gap therefore runs from 3.95 h to the end of the session, 2.08 h with nothing landing. All 10 landings, 6 of them substantive, came in the first 3.95 h. That is about 1.52 substantive per hour, the same as the 09-26 soak's 1.52, and it matches the "about four hours" in PRD §34.

(c) Constant rate at the session average of 1.00 per hour: 9 substantive in 9 h. At the early rate of 1.34 per hour: about 12. Supply-wall model (yield stops once the uncovered-module supply is exhausted at about 3.95 h, with no replenishment): 1.52 × 3.95 ≈ 6, and the total stays near 6 however long the soak runs. That is an average of 0.67 per hour over 9 h. The models differ by a factor of two, which is the whole point of the supply-wall lesson.

(d) At a constant 1.34 per hour, P(no landing in 2.08 h) = e−2.79 ≈ 0.061. At 1.00 per hour it is e−2.08 ≈ 0.125. That is unlikely but not decisive on one soak. What makes it convincing is that the gap is a tail that runs to the end of the session, not a gap in the middle, and that it occurs where PRD §34 says the wall is.

(e) 51 merged in about 9 h is about 5.7 per hour, far above any model in (c). It does not refute the wall. The 10-09 soak ran after the root-cause fixes of 10-08, on a fresh supply, "mostly tests for backend/api/*". The wall is a property of the supply, not of the clock, and a new unexploited area resets it. The figures are also not comparable: the 10-09 row reports no substantive count, and its proof chain read "13 commits verified on main" at its check. The 10-10 row shows why the column matters: 40 entered the funnel and all were refused at promotion.

Conclusion: plan a 9-hour soak around supply, not hours. Without new landable work, expect about 6 substantive landings, nearly all of them in the first four hours.

Challenge 2 (research). The operator's rule in §93.11 is that no training-derived change is pushed until a held-out gain is shown. Design the experiment that would justify pushing an adapter. Givens: the held-out set is 30 tasks from human commits with hidden tests. The served adapter was accepted on 1/30 (unnumbered prompts) or 3/30 (numbered), solved 0, with a mean gain of 0.03. Its handoff gate was 4/6 against the incumbent's 3/6 with one greedy flip. Numbering also moved apply failures from 28 to 21 and syntax failures from 1 to 6 (§93.14). State the hypothesis, metric, control, decision rule and what would falsify it, and work out how much gain 30 tasks can detect.

Hint

Greedy decoding is deterministic, so all the variance comes from the tasks. Compare the two arms on the same tasks and count only the tasks where they disagree.

Worked solution

Hypothesis. The adapter raises the share of held-out tasks solved (hidden tests pass) relative to the incumbent base model under identical conditions.

Metric and control. The primary metric is solved per task, paired: the same 30 tasks, both arms, greedy decoding (as the handoff's own comparison uses). The prompt format is held constant, because §93.14 shows numbering alone moves acceptance from 1/30 to 3/30 and trades apply failures for syntax failures. Use the numbered format, since that is what production's 2b.1-diff path shows the model (§93.8). Apply failures, syntax failures and accepted counts are secondary metrics, so a "gain" that is really a format shift is visible. A contamination check confirms that no held-out task's source commit or target file appears in the training rows. The glossary's definition, "never on training rows", requires that.

Decision rule, fixed in advance. Use an exact one-sided sign test on discordant tasks, those solved by exactly one arm. If all k discordant tasks favour the adapter, p = 0.5k, so at least 5 are needed to reach p ≈ 0.031 < 0.05. The current gate's single flip gives p = 0.5, which is why the project's notes reject 4/6 against 3/6 as evidence. Push only if the rule passes. Otherwise roll back, which the handoff already supports.

Falsification. Fewer than 5 net discordant wins, or at least as many discordant losses as wins, falsifies the hypothesis for this adapter. A gain in "accepted" with no gain in "solved" counts as a format effect, not learning.

Power. The base solves 0 of 30. Suppose the adapter truly solves 10% of tasks. Its solved count is Binomial(30, 0.1), and P(at least 5) = 1 − (0.042 + 0.141 + 0.228 + 0.236 + 0.177) ≈ 0.18. The experiment would miss a real 10-point gain about 82% of the time. Thirty tasks can reliably detect only large gains, roughly 25% or more.

Proposal (mine, not in the paper). Grow the held-out set from new human commits before training on the next corpus, and add a placebo arm: an adapter trained on the same rows with shuffled reward labels. That separates "any adapter changes behaviour" from "this training signal helped". It matters because §93.11 measured a gradient norm of about 1e-4.

Check: the design passes only if the hidden tests the base model fails start passing on several tasks, all in the same direction. A score difference that comes from prompt format or a single flip cannot pass it.

Challenge 3 (adversarial). §93.7 says the promotion gate checks provenance, coverage, and that no public symbol vanished. Open backend/core/ouroboros/governance/accumulation_promotion_gate.py and read verify_commit and the four _check_* functions. Construct three landings, each produced honestly by the sanctioned lane, that try to reach main carrying damage: (1) a whole-file re-emission that keeps every public name but rewrites one function body wrongly; (2) a punctuation-and-quote-only rewrite like f97f8195d6; (3) an edit to a module whose filename stem is shared with an unrelated module elsewhere. For each, say which check stops it, or show honestly that none does and which layer must.

Hint

Count the checks in verify_commit: the paper names three, the code runs four. Then look at how _test_paths_for finds "the" tests for a file.

Worked solution

Setup: verify_commit runs _check_provenance, _check_structure, _check_semantic_delta and _check_coverage, fails closed, and records refusals to LessonMemory. The fourth check is not in the paper's summary. Its docstring says it was added after 7e7fe18c3c (soak bt-2026-09-17-180722), a commit that passed provenance, structure and tests while changing nothing functional. Because all three of our landings come from the lane, each one passes provenance: Op-ID, Session and Files trailers are present, and the session matches the branch.

(1) Body rewritten, names kept. Structure passes: _public_surface collects only module-level public names and __all__, and nothing shrank. Semantic delta passes, because the AST really did change. Coverage runs the stem-matched tests, and the landing passes if those tests do not exercise the broken behaviour. No promotion check stops it. The only defence is test strength, in VALIDATE and again at promotion. §93.10's sse_contract.py landing, whose dropped content was restored by hand, is this class. The root fix is the one §93.15 ranks first: diff output, so the model edits one hunk instead of re-emitting the file.

(2) Punctuation-only rewrite. Today _check_semantic_delta stops it. It compares canonical_ast_dump before and after, and comments, whitespace and quote style do not appear in the AST. It refuses with "no functional change … comments, formatting and quote style only". There is deliberately no threshold, so a real one-character fix still passes. Per §93.10, f97f8195d6 had to be reverted by hand. Nothing in the paper says which checks it met, so this reading is mine: the semantic-delta check is the layer that now closes that class mechanically.

(3) Shared stem. _test_paths_for finds cover with tests_root.rglob("test_<stem>.py"), matching on the filename stem anywhere under tests/. An edit to one utils.py can therefore be "covered" by a test_utils.py written for a different utils.py. If that unrelated test is green, coverage passes while the edited module stays untested. No promotion check stops it. This is a real hole in the coverage check, read from the code. A proposed fix (mine) is to require that a covering test import the touched module, the same "never imports its subject" rule the Test Reality Gate applies to candidate tests (§93.8).

Conclusion: the gate reliably catches shrink (lost exports, a removed __all__, an unparsable file) and no-ops. It does not catch wrong behaviour that tests do not see, and its definition of "covered" can be satisfied by the wrong test. Check your reading by finding the comment added or deleted file — not a shrink in _check_structure. It shows that the structure check also ignores whole-file deletions, which leaves them to coverage.
