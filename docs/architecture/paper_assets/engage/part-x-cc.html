Quick check · §57

1. §57 calls the gate "structural": code paths in the governance layer, not policy documents. What does that difference buy?

A policy document has to be read and obeyed, so it can be misread, ignored or argued with. A code path runs whatever the model writes. That is what lets the paper say no prompt can convince the gate to allow a forbidden action. See §57.

2. How does the Iron Gate make default-allow tools possible?

It is the containment surface around the tools. If the gate reliably refuses forbidden paths, commands and edits, a tool can be enabled by default without trusting the model to use it well. Without the gate, each tool would need its own restriction or an approval. See §57 and §18.3.

3. The gate is deterministic, so the same input always gives the same verdict. Why must every decision also be logged?

Determinism means a verdict can be repeated. The log means it can be audited: someone can see afterwards what was refused or allowed, and why. "Auditable" is listed as a separate property in §57.

Quick check · §58

1. Gate 1 rejects paths containing .., yet it also checks that the resolved path is still within the repo root. Why have the final check?

Rejecting certain strings only covers the patterns someone thought to list. The last rule checks where the path actually points after resolution, which is the property the gate exists to protect: no reads or writes outside the repository. See §58.1.

2. Gate 2 classifies an op that targets a protected path as BLOCKED at CLASSIFY. Why stop it that early, rather than at the tool call?

A BLOCKED op short-circuits before any exploration or generation is spent on a change that could never land. The rule is also enforced at the tool boundary through GoverningToolPolicy Rule 2, so both layers refuse the same paths. See §58.2.

3. Under Gate 7, an op over its per-op cost cap is aborted, but an op that meets an exhausted daily budget is queued. Why the different treatment?

An op over the per-op cap is itself too expensive, so it is aborted. An exhausted daily budget says nothing about the op, only that the day's spend is used up. Queueing keeps the work instead of discarding it. Both are hard ceilings on spend. See §58.7.

Quick check · §59

1. The gate "does not reason about intent". What kind of harmful operation is it therefore blind to by design?

Any operation whose harm lies in what the change means, not in the paths, tokens or commands the gate reads. A change inside allowed paths, using no blocked command, passes no matter what it is for. Judging intent is left to other mechanisms. See §59.

2. The gate is "not an approval queue". How do the gate and approvals divide the work?

The gate enforces the operator's non-negotiable constraints structurally, with one deterministic rule per gate. Approval is a separate mechanism (§14), kept for cases the gate cannot decide, the APPROVAL_REQUIRED tier in §60. See §59.

Quick check · §60

1. Which operations still need a human under §60, and why can the gate not remove them?

Operations in the APPROVAL_REQUIRED tier. The gate replaces approval only for routine operations it can vet structurally. When the gate itself cannot decide, approval remains. See §60.

2. §60 says the Iron Gate is "not an adversarial mechanism against the model". What role does it play instead?

It is the enabling mechanism. Because the operator's non-negotiables are enforced structurally, the model can be given real autonomy inside them, including default-allow tools and auto-apply for low-risk ops. See §60.
