Pause and predict

An image's metadata (path, mime type, short hash) is passed around separately from its bytes. How could a constructor make it impossible for a caller to hand in a mismatched path, mime type and hash, and what else should a safe attachment object refuse to leak?

Reveal the answer

The canonical constructor Attachment.from_file(path, kind=..., app_id=...) computes hash8 from the actual file bytes and infers mime_type from the extension, so the caller never supplies them. __post_init__ then rechecks every field against its whitelist, regex or length cap. The __repr__ is redaction-safe: it shows only the basename and hash8, never the full path. See §84.1.

#### Check your understanding: PART XV — Multi-Modal Perception: The Senses→Mind Bridge

Conceptual questions

1. Most of the pieces for multi-modal input already existed before the arc. Why could the system still not see a single image at GENERATE time?

The parts did not agree on their contracts (§82.2). Producer and consumer disagreed on the sidecar filename, on the timestamp key, and on the hash format (decimal integer versus 16 lowercase hex characters), and the OCR function was never passed to the sensor. Each mismatch made the pipeline fail silently at a different point. Even after fixing these, nothing populated ctx.attachments at intake, the serializer's purpose allow-list lacked "generate", and neither provider called the serializer during code generation. The lesson is that having the components is not the same as having the capability; the connections are where it failed.

2. Why do both ingress paths converge on one ctx.attachments tuple instead of letting the provider handle each source differently?

The Manifesto §1 implication used here is that Body and Mind talk through stable interfaces, not origin-aware dispatch (§83.4). If the provider had to branch on "did this come from Ferrari or from the operator", Body implementation details would leak into the Mind's prompt shaping. With one surface, the provider sees one shape of content block regardless of source. A new ingress, such as a Slack webhook, only adds a kind at the hoist layer and needs zero provider changes (§88).

3. The attachment hoist at intake catches every exception and logs at DEBUG. Is that a safety gap or the right choice?

The paper calls it fail-closed discipline (§83.3). If the frame file vanished, an /attach file was deleted, or a mime check failed, the op is demoted to text-only instead of breaking intake. "Closed" here means no pixels ship when anything is wrong; the op still enters CLASSIFY. The trade-off is visibility: a DEBUG breadcrumb is easy to miss, so an operator might not notice that an op lost its image. The safety boundary is preserved, because a failed check never results in unvalidated bytes being sent.

Worked solution

SerpentFlow._handle_attach() parses the path and description, then runs the validation perimeter: absolute path, file exists, extension in _ATTACHMENT_EXT_TO_MIME, size within the 10 MiB default, and _is_protected_path(path) returns None (§83.2). It builds an envelope with source="voice_human", empty target_files, and evidence["user_attachments"], and calls the intake router's ingest.

In _dispatch, the hoist reads user_attachments, calls Attachment.from_file(path, kind="user_provided"), which computes hash8 and infers image/png, and logs [IntakeRouter] attachments_hoisted ... kind=user_provided. The context gets the tuple via with_attachments (§83.3).

At GENERATE, _serialize_attachments() checks the purpose is allowed, the kill switch is on, attachments exist, and the route is not BG or SPEC, then reads the bytes within budget (§84.4). For Claude it emits an image block, and _generate_raw places it before the text block (§85.1). The provider logs [ClaudeProvider] multi_modal op=... blocks=1 ... mime_kinds=[image/png] (§85.4, §90.2). Grepping the op id finds both lines.

Problem 2 (design). A teammate wants to raise the attachment cap to 32 MiB so long PDFs fit, arguing "Anthropic allows it". Using §84.2, §88 and §89.6, argue for or against, and suggest a better path for long documents.

Hint

Consider base64 inflation, the prompt scaffold, and what §88 says about relaxing gates.

Worked solution

Against. At 10 MiB the base64 payload is about 14 MiB, leaving headroom under Anthropic's 32 MiB limit for system text and tool manifests (§84.2). A 32 MiB file would inflate well past 32 MiB and risk a payload-oversize 400.

The paper also treats the cap as a hard gate. It says relaxing a safety budget to fit a new code path is the anti-pattern that Manifesto §6 forbids, and §88 confirms none of the gates were relaxed.

Even within the cap, §89.6 notes that a long PDF sent as one block can push token counts above the context window. The better path is the future work it describes: per-page extraction with page-range arguments to /attach, or operators pre-summarizing large documents, which the cap already encourages.
